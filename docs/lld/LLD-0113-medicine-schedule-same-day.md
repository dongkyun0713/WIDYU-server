## 1. 목적 / 배경

LLD-0061은 방장의 복약 일정 등록·수정·삭제를 **다음 날부터** 적용했다. 오늘 알람 시간을 바꿔도 오늘은 옛 시간에 울리고, 새 알람은 오늘 울리지 않으며, 삭제해도 오늘 알람이 남는다. 사용자 결정(2026-10-28)으로 **알람 단위로 오늘 끝났는지**에 따라 적용일을 정한다.

- **오늘 끝난 알람**: 오늘 인증했거나, 인증 가능 시간(알람 ±30분)이 지난 미인증 알람. 오늘 기록(완료·미인증)과 알람을 그대로 두고 **다음 날부터** 바꾼다.
- **아직 안 끝난 알람**: 미인증이고 인증 가능 시간이 남은 알람(예정 포함). **오늘부터** 바꾼다.

예) 9시(완료)·13시(예정)·18시(예정)에서 11시에 9시를 12시로 바꾸면 오늘은 9시 완료 그대로, 내일부터 12시. 9시가 미인증이어도 같다. 13시를 15시로 바꾸면 오늘 15시에 울린다.

방장 전용 권한·revision 계약·응답 필드 구조는 LLD-0061 그대로다.

## 2. 범위

### In scope

- 변경 모듈: `widyu-api`만. 엔티티·스키마·enum 변경 없음.
- `MedicineScheduleService`의 등록·수정·삭제 유효기간, 수정 시 오늘 인증 이동, 삭제 시 오늘 인증 보호.
- 알림 문구 M05·M08·M09의 "내일부터" → "오늘부터", Swagger 설명, 테스트.

### Out of scope

- 걷기 목표의 다음 날 적용(`WalkService`), 복약 인증 시간창·포인트 규칙, 인증 날짜 기준 통일(#872).

## 3. 인터페이스 / API

요청·응답 형식은 LLD-0061과 같다. `effectiveFromDate`는 바뀐 내용이 처음 적용되는 날이다.

| 메서드 | `effectiveFromDate` |
| --- | --- |
| POST | 새 알람의 오늘 인증 가능 시간이 남았으면 오늘, 지났으면 내일 |
| PUT | 아직 안 끝난 알람이면 오늘, 끝난 알람이면 내일. 시작 전 버전(배포 전 정책으로 만든 내일 시작 버전)은 그 버전의 시작일 |
| DELETE | 중단이 시작되는 날. 아직 안 끝난 알람이면 오늘, 끝난 알람이면 내일 |

## 4. 데이터 모델

변경 없음. `effectiveFrom <= D <= effectiveTo` 양끝 포함 규칙과 `MedicationProof.moveTo`를 그대로 쓴다.

## 5. 처리 흐름

"끝났다" 판정(`isFinishedToday`): `now > 오늘 알람시각 + 30분`(`MedicationStatus.ALLOWED_WINDOW_MINUTES`) 이거나, 그 스케줄에 오늘 `verifiedAt` 인증이 있으면 끝난 것이다. 인증 가능 시간 안이면 아직 인증할 수 있으므로 안 끝난 것으로 본다.

1. 등록: 새 알람시각의 오늘 인증 가능 시간이 지났으면 내일, 아니면 오늘 시작으로 저장한다.
2. 수정: 적용일 D를 정한다. 오늘 유효하지 않은 버전(시작 전)은 D = 그 버전의 시작일, 오늘 끝난 알람은 D = 내일, 그 외 D = 오늘.
   - 버전이 D 전날에 유효하지 않았으면(오늘 시작·시작 전) 지켜야 할 날짜가 없으므로 in-place로 바꾼다.
   - 아니면 `closeAsOf(D - 1)`로 마감하고 D 시작 새 버전을 저장한다.
   - 오늘 인증은 옮기지 않는다. 인증이 있으면 끝난 알람이라 D = 내일이고 옛 버전이 오늘까지 유효하다. 안 끝난 알람에는 오늘 인증이 없다.
3. 삭제: 오늘 유효하고 끝난 알람이면 `closeAsOf(today)`(오늘 기록 유지, 내일부터 중단), 아니면 `closeAsOf(yesterday)`(오늘부터 중단). 시작 전 버전은 빈 유효기간이 된다.
   - 인증한 알람을 오늘에서 빼지 않는 이유: 인증 처리(`MedicationProofTransactionService`)는 회원의 오늘 인증 수를 스케줄 유효 여부와 무관하게 세고, 분모는 오늘 유효한 스케줄 수다. 빼면 분자가 분모보다 커져 "전부 완료" 포인트가 잘못 지급될 수 있다.
4. revision 증가·변경 신호 enqueue는 기존 `sendAlarmChanged` 그대로 같은 트랜잭션에서 한다.

## 7. 인수조건 (Acceptance Criteria)

- [x] 인증 가능 시간이 남은 시각으로 등록하면 오늘부터, 지난 시각이면 내일부터 유효하다.
- [x] 아직 안 끝난 알람을 수정하면 옛 버전은 어제까지, 새 버전은 오늘부터 유효하다. 오늘 시작한 버전이면 새 버전 없이 같은 버전이 바뀐다.
- [x] 오늘 인증한 알람, 인증 가능 시간이 지난 미인증 알람을 수정하면 옛 버전과 인증이 오늘까지 그대로이고 새 버전은 내일부터다. 오늘 시작한 버전이어도 같다.
- [x] 아직 안 끝난 알람을 삭제하면 오늘부터 유효하지 않다. 끝난 알람을 삭제하면 오늘까지 유효하고 내일부터 유효하지 않다.
- [x] 배포 전 정책으로 만든 내일 시작 버전을 수정·삭제해도 같은 날 유효 버전이 둘이 되지 않는다.
- [x] M05·M08·M09 본문이 "오늘부터"이고 Swagger 설명이 새 규칙과 맞다.
- [x] `MedicineScheduleServiceTest`·`NotificationCopyTest`가 위 경계를 검증하고 관련 테스트가 통과한다. 지난 시각 사례는 00:00 알람으로 검증하며 00:31 이전 실행에서는 건너뛴다.

## 8. 영향 범위 / 마이그레이션

- **LLD-0061 대체:** §5의 3~6(항상 내일 시작)은 이 문서로 대체한다. 권한 규칙(E10)은 유지한다.
- **전환기:** 배포 당일 배포 전에 수정된 일정은 "옛 버전(오늘까지) + 새 버전(내일부터)" 쌍으로 남는다. 그 새 버전을 다시 고치면 in-place로 바뀌고 시작일(내일)을 유지해 겹치지 않는다. 하루 뒤 자연히 해소되므로 데이터 보정은 하지 않는다.
- **이미 지난 시각으로 수정:** 아직 안 끝난 알람(예: 13시)을 이미 지난 시각(예: 10시)으로 바꾸면 사용자 결정대로 오늘부터 적용되어 오늘 10시 알람은 미인증으로 집계된다.
- **알림 문구:** 끝난 알람의 수정·삭제는 실제로 내일부터인데 M05·M09 본문은 "오늘부터"다. 응답·알림 데이터의 `effectiveFromDate`는 정확하다.
- **FE:** `effectiveFromDate`가 오늘이면 오늘 알람 스냅샷(`/alarm-sync`)을 바로 다시 받아 로컬 알람을 교체해야 한다. revision 증가·동기화 신호는 그대로다.
