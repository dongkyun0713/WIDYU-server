# 운영 장애 알림·복원 검증

#604의 운영 하위 작업 #607이다. 설정 파일이 준비됐다는 것과 운영 알림을 수신하고 데이터를 복원했다는 것을 구분한다. 현재 실제 AWS 수신·복원·롤백은 미실행이다. 도메인/API 변경이 없어 LLD는 N/A다.

## 배포 전에 필요한 값

운영 환경 파일에 `PROD_DISCORD_WEBHOOK_URL`을 지정한다. 개발용 `DISCORD_WEBHOOK_URL`과 다른 운영 담당자 채널을 사용한다. URL은 비밀값이므로 문서·터미널 출력·Git에 넣지 않는다. 잘못된 HTTPS Discord URL은 배포 사전 검사에서 거절한다. 기존 운영 환경에는 이 값을 추가해야 다음 배포가 진행된다.

운영 Compose는 `monitoring/grafana/alerting-prod`만 alerting provisioning 경로에 읽기 전용으로 마운트한다. 운영 Prometheus는 같은 Compose의 API·Node Exporter를 조회한다. 개발 규칙은 수정하지 않는다. 이 알림은 내부 담당자용이며 이용자 공지 위치·문구를 정하지 않는다.

## 기본 감지 기준

아래 값은 이번 구성의 시작값이며 서비스 SLO나 기획 승인으로 간주하지 않는다. 첫 운영 주간의 요청량·오탐을 보고 변경한다.

| 대상 | 발동 기준 | 데이터 없음 |
| --- | --- | --- |
| API 수집 | up=0 또는 타깃 지표 없음, 1분 유지 | 알림 |
| API 오류 | 최근 5분 5xx 3건 이상이며 오류율 5% 초과, 1분 유지 | 정상 취급, 별도 수집 중단 규칙 확인 |
| 디스크 | 루트 파일시스템 가용량 15% 미만, 5분 유지 | 알림 |
| 호스트 지표 수집 | Node Exporter up=0 또는 지표 없음, 2분 유지 | 알림 |

평가 간격 1분·통지 대기 30초 때문에 조건 시간 즉시 수신되는 것은 아니다. 쿼리 오류는 Alerting으로 처리한다. Grafana 자체가 멈추면 통지할 수 없다. 메트릭 기반 통지에는 오류 원문·토큰·인증번호를 포함하지 않는다.

## 실제 수신 검증

1. 별도 검증 환경에서 Grafana provisioning 오류가 없는지 확인한다. 운영 대시보드에서 규칙 4개·운영 수신처·운영 라우팅을 확인한다. 기존 볼륨에 수동으로 만든 규칙이 있으면 영향 확인 후 별도로 정리하며 자동 삭제하지 않는다.
2. 운영 담당자가 승인한 테스트 메시지를 보내 수신자·수신 시각을 기록한다. Contact point 테스트만으로 지표 감지까지 검증했다고 표시하지 않는다.
3. 검증 환경 API만 중지한 뒤 firing→수신→재기동→resolved를 확인한다. 운영 API·RDS를 임의 중단하지 않는다.
4. 검증 환경의 합성 5xx 요청으로 오류율 규칙을 확인한다. 오류 3건 미만·정상 트래픽·무트래픽 때 오탐 여부도 확인한다.
5. 디스크를 실제로 채우지 않는다. 검증 환경의 테스트 데이터소스 또는 임시 임계치로 firing/복구를 확인하고 원래 규칙으로 복구한다. 실제 호스트 루트 지표가 조회되는지도 별도로 확인한다.
6. Grafana/Prometheus 중단도 검사한다. 이 경우 같은 EC2 내부 규칙만으로는 수신을 보장하지 못한다.

## EC2 전체 중단을 위한 외부 경로

운영 담당자가 대상 리전·인스턴스·SNS 이메일을 확정한 뒤 CloudWatch의 EC2 상태 검사 알림을 구성하고 이메일 구독을 승인한다. 자동 재부팅·종료 작업은 연결하지 않는다. EC2 상태 검사만으로 앱 응답 실패나 의도적인 인스턴스 정지를 모두 검출한다고 가정하지 않는다. 다른 장애 영역에서 공개 HTTPS health를 점검하는 외부 감시와 지표 누락 감지도 함께 준비한다.

외부 감시 서비스와 비용은 아직 선택하지 않았다. AWS 전체 합산 월 8~9만 원 안에서 EC2·RDS·스토리지·백업·전송·IP·모니터링·세금을 함께 계산한다. AWS Budgets는 비용 알림이지 지출 자동 차단이 아니다. 이 작업에서는 유료 자원을 만들지 않았다.

## RDS 복원 연습

1. 담당자·실행일·허용 데이터 손실(RPO)·서비스 복구 목표(RTO)을 먼저 기록한다. 미정 값을 임의로 통과 기준으로 쓰지 않는다.
2. 운영 RDS의 자동 백업 보관 기간과 복원 가능한 시각을 읽기 전용으로 확인한다. 테스트용 RDS 생성 비용·보안 그룹·자격증명 분리를 승인받는다.
3. 기존 운영 DB를 덮어쓰지 않고 새 비공개 DB에 선택 시점으로 복원한다. 복원 시작·DB 준비 시각을 기록한다.
4. 앱을 격리해 연결한다. PG·문자·FCM·스케줄러의 실제 외부 부작용을 차단한 상태에서 회원·가족·앨범·결제·포인트를 조회한다. 결제 원장과 포인트 이력·잔액을 대조한다.
5. 서비스 조회 완료까지의 시간을 RTO와 비교한다. 마지막 복구 데이터 시각과 장애 기준 시각의 차이를 RPO와 비교한다. DB가 available인 시각만으로 복구 완료를 판정하지 않는다.
6. 정리 대상 테스트 리소스 ID를 확인하고 담당자 승인 후 정리한다. 운영 RDS·원본 백업·공유 버킷은 삭제하지 않는다.

## S3 복원 연습

버전 관리 상태·수명 주기 규칙·이전 버전 보관 기간을 확인한다. 별도 테스트 객체로 덮어쓰기·삭제 후 이전 버전을 새 검증 키로 복사하고 크기·체크섬·실제 앱 조회를 확인한다. 버전 관리 설정 전 삭제된 파일까지 복구된다고 가정하지 않는다. 원본 객체의 버전이나 삭제 마커를 운영에서 임의 제거하지 않는다.

## 롤백 연습

검증 DB에 새 스키마를 적용한 뒤 새 앱과 이전 SHA 이미지를 차례로 실행한다. 컬럼 추가 등 확장 변경과 구버전 호환을 확인하고 파괴적인 다운 마이그레이션은 사용하지 않는다. 이전 앱의 로그인·가족 조회·앨범·WebSocket 재연결·결제 대역 흐름을 확인한다. 실행 명령은 [운영 배포의 수동 복원](../production-deployment.md#장애-확인과-수동-복원)을 따른다.

로컬 fake Docker 회귀는 명령 순서·실패 전파를 검증할 뿐 실제 컨테이너 롤백을 증명하지 않는다. `down -v`, reset, clean으로 롤백하지 않는다.
