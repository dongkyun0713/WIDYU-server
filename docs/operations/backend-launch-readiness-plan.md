# WIDYU 출시 준비 실행 계획

현재 출시 판단은 **보류(REQUEST_CHANGES)**다. 가족 외 실시간 데이터 접근, 계정 정지 후 접근, 운영 장애 감지 등 출시 차단 항목을 해결하고 실제 환경의 검증 증거를 확보해야 한다. 이 문서는 후속 구현 계획이며, 작성 완료가 취약점 수정이나 출시 승인을 의미하지 않는다.

- 작성일: 2026-09-14 / 상태: 실행 계획 검토안
- 문서 작업: [#601](https://github.com/GB-able/WIDYU-server/issues/601)
- 점검 기준: `feature/599`, `b4d3ffb`. 이후 변경은 구현 착수 시 재대조한다.
- 대상: 백엔드·앱 개발자, 운영 담당자, 출시 승인자
- 기획 결정: [출시 정책 검토서](../policy/launch-policy-review.md)

- 기준 문서: [운영 배포](../production-deployment.md), [개인정보 저장 암호화](../adr/ADR-0025-pii-at-rest-encryption-policy.md)

## 1. 확정 조건과 검증 전제

`확정`은 합의한 요구사항이지 현재 구현·운영 검증이 완료됐다는 뜻이 아니다. `제안` 수치는 후속 설계·부하 실험·기획 검토에서 승인해야 한다.

| 구분 | 조건 | 상태 |
| --- | --- | --- |
| 비용 | AWS 전체 합산 월 80,000원 목표, 90,000원 상한 목표. EC2만의 예산이 아님 | 확정 |
| 서버 | EC2 t4g.medium 유지, RDS 유지. EC2에 MySQL 합치기나 EC2 축소는 범위 밖 | 확정 |
| 시험 부하 | 동시 활성 사용자 50명, 시니어 20명이 각 초당 심박 1건, 일반 HTTP 평균 10 RPS·순간 30 RPS | 확정 |
| 복구 | DB RPO 5분, 서비스 RTO 2시간 | 확정 목표, 실측 필요 |
| 알림 | 운영 Discord와 이메일, EC2 외부 감지 경로 | 확정 방향 |
| 세션 | 로그아웃·비밀번호 변경·정지·탈퇴 시 모든 기기 접근 종료 | 확정 |
| 탈퇴 | 작성자 소유 앨범·프로필·복약 이미지 삭제 | 확정. 유료 열람 보상은 미결정 |
| 앱 호환 | 페이징 API를 추가하고 앱 전환 후 기존 API 폐기 | 확정. 보안·동의 검증 우회는 유지하지 않음 |
| 개인정보 | 한국 서비스 기준 검토. 앱 동의 UI와 서버 동의 기록 추가 | 확정 방향, 문안·기간·법률 적용은 검토 필요 |

실제 AWS 계정의 리전, RDS 사양·스토리지, 세금·할인, 최근 청구액, 기존 앱 지원 버전은 확인되지 않았다. 24시간 가동·크레딧 제외를 견적 기준으로 제안한다. 비용·성능·복구 목표를 동시에 달성할 수 있다고 아직 단정하지 않는다.

## 2. 증거 수준과 실행 순서

### 기존 점검 결과

아래는 전달된 기존 점검 결과다. 이 문서 작업에서 재실행한 결과로 취급하지 않는다.

- Domain 28건, API 526건으로 총 554건 통과. 처음 건너뛴 Redis 6건은 임시 Redis로 별도 실행해 통과했고 임시 Redis는 종료했다.
- 운영 Compose·배포 회귀 9건 및 릴리스 Java 정적 검사 통과.
- WebSocket `/topic/**` 구독이 타 가족 심박·위치 토픽과 매칭되고 브로커 토픽 직접 전송이 전달되는 동작을 프로젝트 인터셉터와 Spring 구독 레지스트리로 로컬 재현했다.
- 관리자 재발급의 고정 ADMIN 발급은 계획 수립 중 추가로 코드 확인했다. 실제 운영 권한 상승 요청을 실행했다는 뜻은 아니다.
- AWS 설정 조회, 운영 두 계정 검증, 알림 수신, 백업 복원, 롤백, 구버전 앱, 실제 MySQL 동시성·부하 실험은 미실행이다.

### 실행 순서와 담당

담당은 역할 지정이다. 실제 담당자·백업 담당자·일정은 착수 회의에서 기입한다. 종료일은 선행 단계 증거와 작업량을 확인한 뒤 확정한다.

| 순서 | 작업 묶음 | 책임 역할 | 선행 조건 | 완료 산출물 |
| --- | --- | --- | --- | --- |
| 0 | SEC-01~04 접근 차단, POL-01~04 정책 확인 | 백엔드 / 기획 | 현 코드 재대조 | 보안 LLD, 우회·폐기 회귀 테스트 |
| 1 | DAT-01 정합성, EXT-01 발송 분리 | 백엔드 / QA | 인증 경계 확정 | MySQL 장애·동시성 결과, 실패 재처리 화면 |
| 2 | OPS-01 알림, BAK-01 복구, COST-01 견적 | 운영 / 백엔드 | 실제 AWS 읽기 권한·수신처 | 알림 수신 기록, 복구 시간, 월 견적 |
| 3 | REL-01 배포, PRIV-01 동의·삭제, PERF-01 부하 | 백엔드 / 앱 / 기획 | 정책 승인·안전한 코드 기준선 | 호환·삭제·부하 시험 결과 |
| 4 | 출시 시나리오 종합 검증 | QA / 운영 / 출시 승인자 | 모든 차단 항목 해소 | 승인자와 증거가 기록된 출시 판정 |

정책 검토·견적·운영 준비는 보안 수정과 병행할 수 있다. 접근 권한 오류, 결제 오반영, 동의 없는 민감정보 처리, 복구 불가를 잔여 위험으로 단순 수용하지 않는다. 해당 기능을 제외하려면 기획 승인과 서버·앱 비활성화 검증이 필요하다.

## 3. 인증·인가·보안

### SEC-01 관리자 권한 상승 차단 — 최우선 출시 차단

현재 [AdminAuthService](../../backend/widyu-api/src/main/java/com/widyu/admin/application/AdminAuthService.java)의 `refresh`는 재발급 토큰의 회원 ID로 역할을 재조회하지 않고 ADMIN 토큰을 발급한다. 일반 회원의 유효한 재발급 토큰을 관리자 쿠키에 넣는 경우를 차단해야 한다.

1. 관리자 로그인·재발급 모두 DB의 실제 역할과 활성 상태를 확인한다.
2. 관리자 API도 토큰 역할만으로 승인하지 않는다. 이미 발급된 잘못된 ADMIN 토큰과 역할 변경 전 토큰의 접근을 차단한다.
3. 관리자 로그아웃은 쿠키 삭제와 서버 측 전체 세션 폐기를 함께 수행한다.

완료 조건: 일반 회원 토큰을 `admin_refresh_token`으로 제출하면 실패한다. 정지·강등된 관리자와 이미 발급된 잘못된 권한 토큰도 REST·재발급에 접근할 수 없다. 정상 관리자 흐름은 유지한다.

### SEC-02 WebSocket 가족 인가와 발송 경로

대상: [JwtChannelInterceptor](../../backend/widyu-api/src/main/java/com/widyu/global/websocket/JwtChannelInterceptor.java), [가족 접근 ADR](../adr/ADR-0020-family-access-dual-path.md).

- SUBSCRIBE는 명시한 목적지만 허용한다. `/topic/heart-rate/{숫자 seniorId}`, `/topic/location/senior/{숫자 seniorId}`는 해당 회원의 가족 관계를 검사한다.
- 개인 결과·오류 큐는 호출자 본인의 `/user/queue/heart-rate/result`, `/user/queue/location/ack`, `/user/queue/errors` 계약을 확인해 허용한다. 새 목적지를 추가하면 인가 테스트도 추가한다.
- `/topic/**`, 임의 와일드카드, 잘못된 ID와 알 수 없는 목적지는 거절한다.
- SEND는 `/app/location/update`, `/app/heart-rate/send-single`만 허용하는 방향으로 실제 앱 계약을 대조한다. `/topic/**` 등 브로커 목적지 직접 전송은 차단한다.
- CONNECT의 JWT·일회용 WS 토큰에 동일한 회원 상태 검사를 적용한다. 정상 heartbeat·UNSUBSCRIBE·DISCONNECT 처리는 유지한다.
- 가족 해제·정지·탈퇴·로그아웃·동의 철회 시 기존 연결과 구독도 무효화한다. 연결 종료 전 경합에서도 권한 없는 수신자에게 신규 메시지를 보내지 않도록 검증한다.

완료 조건: A/B 가족으로 REST·구독·직접 SEND·일회용 토큰·연결 후 가족 해제를 검사한다. 타 가족 메시지 수신 0건, 본인 ACK 정상 수신, 브로커 직접 발송 0건을 입증한다.

### SEC-03 전체 기기 세션 폐기

제안 설계: 회원 인증 버전을 DB에 두고 토큰에 버전을 기록한다. 로그아웃·비밀번호 변경·정지·탈퇴 시 버전을 원자적으로 올리고 재발급 토큰·WS 연결을 정리한다. Redis 삭제 실패로 폐기된 권한이 되살아나지 않게 DB 상태를 최종 기준으로 삼는다.

- 로그인·재발급·REST·WebSocket·현재 회원 조회에서 활성 상태와 인증 버전을 일관되게 검사한다.
- 정지와 탈퇴를 구분한다. `withdrawnAt` 등으로 탈퇴를 식별하며 단순 상태 변경으로 탈퇴 계정을 복구하지 않는다. 기존 INACTIVE 데이터는 확인 없이 모두 정지로 분류하지 않는다.
- 재발급과 폐기의 동시 요청을 직렬화하거나 동등한 원자성으로 처리한다. 폐기 이후 유효한 토큰이 남으면 실패다.
- 버전 없는 기존 토큰은 이행 정책을 명시한다. 초기 버전으로 제한 수용하더라도 DB 실제 역할·상태를 확인하며, 불명확하면 재로그인을 요구한다.
- 인증 실패 401, 권한·동의 부족 403의 세부 코드, 횟수 제한 429와 `Retry-After`를 앱 계약으로 정한다.

완료 조건: 기기 2대의 access/refresh/WS가 모두 차단되고 재로그인 정책에 맞게만 복구된다. Redis 실패·재발급 경합·정지 해제·탈퇴 재활성화 시나리오를 포함한다. 정책: POL-01.

### SEC-04 자원 남용과 비밀정보 노출

아래 값은 제안이며 기획의 POL-05 승인 후 구현한다.

| 대상 | 제안 한도 | 실패 동작 |
| --- | --- | --- |
| 인증 문자 | 전화번호별 60초 간격, 시간당 3회·일 10회 | 429, 재시도 가능 시각 안내 |
| 문자 발송 IP | 시간당 30회 | 공유망 오탐을 관측하고 조정 |
| 인증번호 검증 | 코드별 실패 5회 | 코드 무효화, 새 발급 필요 |
| 로그인 | 계정별 15분 내 실패 10회, IP별 100회 | 임시 대기, 영구 정지와 구분 |
| 유료 발송 전체 | 서비스 일 총량 별도 확정 | 초과 자동 발송 중단·운영 알림 |

- 전화번호 정규화, 카운터 증가·TTL·인증번호 1회 소비를 원자적으로 처리한다. Redis 장애 시 문자 무제한 발송 대신 503으로 제한한다.
- 운영 Naver 테스트 인증 경로와 원문 JWT·재발급 토큰·인증번호 로그를 제거하거나 운영에서 차단한다. 로그와 오류 응답의 비밀정보 비노출을 시험한다.
- DB·Redis 제한 접근, HTTPS, 비밀키 분리와 관리자 최소 권한을 확인한다. Actuator 공개 health는 최소 정보만 제공하고 metrics/prometheus는 내부 접근으로 제한한다.

## 4. 데이터 정합성

### DAT-01 기존 결제 기반을 실제 MySQL에서 검증

[승인 멱등성](../lld/LLD-0016-payment-confirmation-idempotency.md), [부분 취소](../lld/LLD-0017-payment-partial-cancel-idempotency.md), [PG 트랜잭션 분리](../lld/LLD-0022-payment-pg-call-transaction-separation.md)를 유지한다. 서버 금액·소유권 검사, DB claim → 트랜잭션 밖 PG → DB finalize, PG 멱등 키와 복구 작업을 재사용한다.

| 실험 | 확인할 결과 |
| --- | --- |
| 승인·부분 취소 동일 요청 동시 실행 | 논리 작업당 1회 반영, 원래 멱등 키 재사용 |
| PG 성공 직후 DB 커밋 실패·프로세스 종료 | 조회·복구 후 PG와 DB 금액·상태 일치 |
| 응답 유실 후 앱 재시도 | 새 결제나 중복 포인트 없음 |
| 앨범 해제·목표 보상·관리자 지급 동시 실행 | 잔액과 이력 일치, 중복 차감·지급 없음 |
| 승인·취소·탈퇴 경합 | 허용된 상태 전이만 반영, 실패 이유 기록 |

실제 스키마의 UNIQUE·NOT NULL·참조 무결성·잠금·`@Version` 적용을 확인한다. 관리자 지급도 작업 식별자와 중복 방지 제약이 필요하다. H2나 mock 테스트만으로 동시성 검증을 대체하지 않는다.

중단된 작업의 운영 조회·재처리는 기존 작업 키와 PG 상태 조회를 사용한다. 새 결제를 무조건 호출하지 않는다. 백업 복원 후에는 복원 시점 이후 PG 거래를 대조하고 내부 이력을 복구한 뒤 결제를 재개한다. 완료 증거에는 요청 수, 논리 작업 수, PG 거래·포인트 이력·잔액 대조 결과를 남긴다.

## 5. 장애 감지와 운영

### OPS-01 운영 수신까지 검증하는 알림

현재 수집 기반과 [개발 관측 문서](development-observability.md)는 운영 알림 완성의 증거가 아니다. 운영용 규칙·라벨·Discord 수신처·이메일을 별도로 구성한다. 요청 ID로 로그를 연결하되 metric label에 회원 ID·토큰·원문 URL 등 고유값을 넣지 않는다.

| 신호 | 초기 제안 임계치 | 대응 |
| --- | --- | --- |
| 외부 HTTPS | 1분마다 검사, 3회 연속 실패 | 이메일·Discord, 담당자 확인 |
| 일반 HTTP 5xx | 5분 오류율 1% 초과, 요청 100건 이상 | 배포·DB·외부 의존성 확인 |
| HTTP 지연 | 5분 p95 500ms 초과 | p99·DB 풀·느린 쿼리 확인 |
| 디스크 | 사용률 80% 경고, 90% 긴급 | 원인 확인·안전한 정리, 임의 DB 삭제 금지 |
| DB 풀 | 대기 요청 1분 지속 | 활성 연결·긴 트랜잭션 확인 |
| 복구 작업 | 결제 재처리 중단·파일 최종 삭제 실패 | 실패 작업 조회·담당자 조치 |

EC2 전체가 멈추면 같은 호스트의 Prometheus·Loki도 멈춘다. 저빈도 EventBridge → VPC 밖 Lambda의 공개 HTTPS 검사 → CloudWatch → SNS 이메일을 외부 경로로 제안한다. 검사 함수 실패·데이터 누락도 감지하고 TLS 검증을 끄지 않는다. 이 비용도 AWS 예산에 포함한다.

일반 운영 로그 30일 및 디스크 용량 상한을 제안한다. 개인정보 접근 감사 로그는 별도 기준이다. CPU·메모리·디스크·DB 연결·느린 쿼리와 HTTP p95/p99를 수집한다. health 외에 테스트 계정의 핵심 읽기 흐름도 점검하되 유료·파괴 작업은 실행하지 않는다.

완료 조건: 서버 중단·오류 증가·디스크 임계치·검사기 장애에서 담당자와 백업 담당자가 실제 알림을 수신한다. 감지·수신·확인 시각, 대응 절차, 오탐 조정 근거를 남긴다. 장애 공지 기준은 POL-10에서 확정한다.

## 6. 백업과 복구

### BAK-01 DB·파일·Redis별 복구 기준

- RDS 자동 백업 7일, 암호화·삭제 보호를 기본안으로 제안한다. 실제 설정과 `LatestRestorableTime` 지연을 측정해 RPO 5분을 검증한다. 시점 복원 기능의 존재가 서비스 목표 달성을 보장하지 않는다. [RDS 시점 복원](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)
- 격리된 새 DB에 복원한다. PG·문자·푸시 등 외부 부수효과를 먼저 차단한다. 회원·가족·결제·앨범 조회, 금액 대조, 삭제·동의 철회 이력 반영 후 접속 전환을 연습한다.
- RTO는 장애 감지부터 복원·검증·접속 전환·핵심 기능 정상화까지 측정한다. DB 생성 시간만으로 2시간 충족을 판단하지 않는다.
- S3 버전 관리와 이전 버전 7일 보관을 사고 복구안으로 제안한다. 개인정보 삭제 요청에는 현재·과거 버전, 파생 파일, 캐시·URL 접근까지 별도 삭제 경로가 필요하다. 이용자가 이미 내려받은 파일 회수는 보장할 수 없다.
- 삭제·동의 철회 원장은 DB 복원 세트와 독립적으로 보존·복구할 수 있어야 한다. 과거 백업 복원 후 재적용해 탈퇴 자료가 다시 노출되지 않게 한다. 원장 자체의 최소 항목·보관 기간·접근 권한도 승인한다.

| Redis 용도 | 유실 시 동작 | 준비할 조치 |
| --- | --- | --- |
| 인증·재발급 | 재로그인·재인증 | DB 폐기 상태 유지, 권한 자동 복구 금지 |
| 최신 심박 캐시 | DB 최신 기록 조회 또는 없음 표시 | 저장 시각 표시 |
| 최신 위치·경로 | 새 위치 수신 전 사용 불가 | 이전 값을 현재 위치로 표시하지 않음 |
| 카운터·일회용 코드 | 보수적으로 제한 | 무제한 발송·코드 재사용 금지 |

현재 `256MB + allkeys-lru`는 TTL이 남은 데이터도 제거할 수 있다. `noeviction`과 키별 크기·건수 제한을 제안하지만 설정 변경만으로 안전해지지는 않는다. 메모리 포화 시 쓰기 실패·인증 실패·운영 알림까지 시험한다. 위치 리스트는 TTL 갱신 외에 기록별 시간·개수 상한을 둔다. RDB/AOF 잔존 데이터와 복구 필요성을 검토하며 운영 영속화를 임의로 끄지 않는다. 금전성 정합성의 유일한 근거를 Redis에 두지 않는다.

완료 증거: 백업 설정, 복원 대상·시점, 데이터 손실 간격, 단계별 시간, 개인정보 재삭제·PG 대조·정상 조회 결과, 복구 담당자와 절차. 비밀정보·실제 개인정보는 증거에 첨부하지 않는다.

## 7. 배포와 구버전 앱 호환

### REL-01 재현 가능한 배포·마이그레이션·롤백

- Flyway 기반 이력 관리를 제안한다. 현재 Spring Boot BOM과 호환되는 의존성을 검증한다. 기존 DB는 스키마 비교·백업 후 명시적으로 baseline 처리하며 자동 baseline으로 누락을 숨기지 않는다.
- 컬럼 추가 → 데이터 채우기 → 새 코드 사용 → 구버전 미사용 확인 → 나중 삭제 순서를 지킨다. 운영 `ddl-auto=validate`를 유지한다.
- 페이지 조회 API를 추가하고 기존 앱을 먼저 전환한다. 기존 API 결과를 조용히 잘라내지 않는다. 전환 기간 무제한 조회의 성능이 미달하면 앱 전환이나 출시 범위를 먼저 조정한다.
- 구버전에서 인증 폐기·필수 동의·429 오류 표시를 실제 앱으로 확인한다. 보안 취약 동작을 호환성 명목으로 유지하지 않는다.
- API·관리자·AI 이미지를 버전 또는 digest로 고정한다. 배포·롤백 시점의 이미지와 DB 버전을 기록한다.
- 현재 배포의 SSH 접근과 운영 보안 그룹 방침을 대조한다. GitHub OIDC + SSM 배포를 제안하며 최소 IAM 권한, 명령 실패 전파, 비밀정보 비노출을 검증한다.
- 정상 종료 대기와 컨테이너 종료 유예를 확인한다. 기존 30초/45초 설정만으로 처리 중 작업의 복구를 보장하지 말고 비동기 작업의 lease·재시작 처리를 시험한다.

완료 조건: 새 서버+기존 앱, 이전의 안전한 서버+변경 DB, 배포 실패+롤백을 통과한다. SEC 수정 전 취약 버전은 롤백 대상으로 삼지 않는다. 안전한 롤백 버전이 없으면 점검 모드를 사용한다. 앱 버전·빌드와 마이그레이션 번호를 증거에 적는다.

## 8. 외부 서비스 실패

### EXT-01 FCM 영속 발송과 제한된 재시도

현재 [FcmService](../../backend/widyu-api/src/main/java/com/widyu/fcm/application/FcmService.java)의 타임아웃 없는 동기 호출과 트랜잭션 점유를 분리한다. [복약 사진 삭제 재시도](../lld/LLD-0030-medication-proof-image-deletion-retry.md)의 영속 작업·lease 경험을 참고하되 알림 계약은 별도 설계한다.

1. 업무 변경과 알림 작업 저장을 같은 DB 트랜잭션으로 커밋한다. 도메인 간 전달은 이벤트를 사용하되 커밋과 작업 저장 사이의 유실 구간을 만들지 않는다.
2. 발송기는 짧게 작업을 claim한 뒤 트랜잭션 밖에서 FCM을 호출한다. lease·소유권 검증으로 오래된 작업자의 결과 덮어쓰기를 막는다.
3. 이벤트·수신 대상별 중복 저장을 막는다. FCM 성공 후 DB 반영 전 종료하면 중복 전달 가능성이 있으므로 정확히 1회 수신을 약속하지 않는다. 앱 notificationId 기반 중복 처리는 별도 계약이다.
4. 연결 2초·응답 5초, 최초 포함 최대 5회, 대기 15·60·180·600초를 초기안으로 제안한다. 429·일시 5xx·네트워크 오류만 제한 재시도한다. `Retry-After`와 유효기간을 함께 적용하고 영구 무효 토큰은 비활성화한다.
5. 긴급 알림은 원래 사건 시각부터 5분, 일반 알림은 24시간까지만 재시도하는 안을 기획 승인받는다. 만료된 사건을 현재 긴급 상황처럼 보내지 않는다.
6. 발송 직전에 수신자 활성 상태·가족 관계·동의를 재확인한다. 업무 성공을 푸시 실패로 되돌리지 않고 최종 실패는 운영 조회·수동 재처리·알림으로 남긴다.

알림 작업이 결제 복구를 막지 않도록 실행 풀·큐·처리량을 제한한다. 관리자 테스트 발송도 타임아웃·횟수 제한을 적용하고 작업 접수와 기기 도착을 구분한다.

| 연동 | 구현 시 확인할 사항 | 최종 실패 처리 |
| --- | --- | --- |
| PG | 기존 타임아웃·멱등 키·상태 조회 유지, 부작용 무조건 재시도 금지 | 중단 작업 대조·재처리 |
| OAuth | 타임아웃, 코드 재사용과 제공자 오류 구분 | 재로그인 안내, 토큰 비노출 |
| SMS | 공급자 타임아웃·일일 총량·중복 발송 비용 | 제한된 재시도·발송 상태 조회 |
| S3 | 업로드·삭제 시간과 크기 제한 | 임시 파일 정리·영속 삭제 재시도 |
| AI | 제한 시간·실패 응답·동시 호출 상한 | 결과 없음/지연 표시, 측정값 정합성 유지 |
| 웹훅 | 발신 검증·재전송·순서 역전·중복 사건 | 원래 사건 기준 기록·대조 |

완료 조건: 지연·타임아웃·429·5xx·영구 오류·프로세스 종료·수신 권한 철회를 주입해 업무 커밋, 재시도 횟수, 만료, 최종 실패 상태와 운영 조회를 검증한다.

## 9. 성능과 자원 제한

### PERF-01 고정 인프라에서 부하와 데이터 크기 검증

- 일반 HTTP 앨범 40%·목표 30%·마이페이지 20%·기타 10%를 초기안으로 사용하고 실제 이용 비중으로 보정한다. 심박 20건/초를 일반 HTTP와 동시에 발생시킨다.
- 절차 제안: 예열 5분 → 10 RPS 30분 → 30 RPS 5분 → 회복 10분. 실 AI와 대역 AI 결과를 구분한다. CPU 크레딧·작업 적체를 보는 장시간 시험도 필요하다.
- 초기 통과 목표: 일반 HTTP p95 < 500ms·p99 < 1초, 심박 ACK p95 < 2초·p99 < 5초, 정상 요청의 5xx < 1%. 의도적 401/403/429와 PG·대용량 업로드는 별도 집계한다. ACK와 AI 판정 완료도 구분한다.
- 심박 20건/초가 24시간 계속되면 하루 1,728,000건, 30일 51,840,000건이다. 실제 측정 지속 비율은 미확인이다. 이 상한 또는 승인된 이용 모델로 테이블·인덱스·백업·정리 비용을 산정한다.
- 주요 쿼리 실행 계획·쿼리 수·N+1·페이지 크기·응답 바이트를 확인한다. 포인트 이력은 추가 페이징 API와 집계를 준비한다. 보관 만료 삭제도 작은 배치로 제한한다.
- Hikari 최대 10개를 초기안으로 검토하되 앱·관리 작업·마이그레이션·배포 중 중복 인스턴스의 연결 합계를 실제 RDS 연결 예산과 비교한다.
- 파일 크기·개수뿐 아니라 동시 업로드·사용자 일일량·미완료 multipart 정리·작업 시간·큐 길이를 제한한다. 기존 경로별 업로드 계약을 조용히 축소하지 않는다.
- EC2 CPU 크레딧 잔액과 초과 과금, Redis 포화, JVM·AI·관측 도구의 합산 메모리·디스크를 측정한다. 부하 후 잔액·이력·작업 유실도 대조한다.

완료 조건: 데이터 크기·API 비율·실제 RDS 사양·AI 종류·지연·오류·정합성·월 비용 환산을 기록한다. 목표 미달이면 원인 제거 또는 트래픽·예산 재합의를 진행한다. EC2 축소나 RDS 제거를 임의로 확정하지 않는다.

## 10. 개인정보·정책·비용

### PRIV-01 동의·삭제·접근 기록

- 앱에 목적별 동의·철회 화면을 추가하고 서버에 대상·목적·문서 버전·시각·철회를 기록한다. 기존 이용자의 동의를 임의로 생성하지 않는다.
- 일반 이용·건강정보·위치 수집과 가족 공유의 법적 근거를 구분한다. 가족 연결을 당사자 동의나 법정 대리권으로 간주하지 않는다. 미동의 시 관련 기능만 제한하는 계약을 정한다. 세부 검토는 정책서 POL-02~04와 법률 항목을 따른다.
- 탈퇴 즉시 접근을 막고 작성자 앨범·프로필·복약 사진 삭제를 영속 작업으로 처리한다. 물리 삭제 24시간은 제안 목표이며 실패를 성공 처리하지 않는다. 법정 보관 자료는 목적별로 분리한다.
- 운영자의 개인정보 조회·검색·내보내기·권한 변경 기록을 남긴다. 민감정보 처리 시스템의 접속기록은 정책서의 2년 이상 기준 적용 검토를 따르고 위변조 방지·정기 점검을 설계한다. 일반 디버그 로그와 구분한다.
- 임시 업로드·오래된 로그·실패 작업의 정리 정책과 삭제 증거를 마련한다. 서버·백업 암호화와 기존 소셜 refresh token 암호화 정책을 유지한다.

단가·추가 과금은 [EC2 요금](https://aws.amazon.com/ec2/pricing/on-demand/)과 [RDS MySQL 요금](https://aws.amazon.com/rds/mysql/pricing/)에서 실제 조건으로 산정한다. 무료 크레딧을 상시 운영 가능성의 근거로 삼지 않는다.

AWS Budgets의 실제·예측 알림은 90,000원 기준 50%·80%·100%를 초기안으로 검토한다. 청구 통화가 다르면 환율을 반영한다. 예산 알림은 집계 지연이 있으며 요금을 자동으로 막는 상한 장치가 아니다. [AWS Budgets 동작과 한계](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)

문자·PG 등 AWS 외부 유료 API는 별도로 집계·제한한다. 초과 예상 시 미완료 업로드 정리·비핵심 작업 조절·사용량 한도를 검토하되 백업·인가·감사 기록을 없애 비용을 맞추지 않는다. 고정 사양·부하·복구 목표와 예산이 충돌하면 출시 승인자에게 재합의를 요청한다.

## 11. 출시 승인 체크리스트

각 항목에 담당자, 실행일, 빌드·환경, 증거 링크, 결과를 채운다. 테스트 예정·설정 파일 존재·문서 작성은 통과가 아니다.

- [ ] 일반 회원 토큰으로 관리자 토큰을 발급하거나 관리자 API에 접근할 수 없다.
- [ ] 다른 가족 데이터의 REST·WebSocket 접근과 브로커 직접 발송이 차단된다.
- [ ] 로그아웃·비밀번호 변경·정지·탈퇴·가족 해제 후 기존 연결까지 정책대로 차단된다.
- [ ] 로그인·문자·업로드 제한과 비밀정보 비노출을 검증했다.
- [ ] 실제 MySQL 동시 요청·PG 부분 실패 후 잔액·상태·이력이 정확하다.
- [ ] 외부 API 지연·실패가 유한 시간 안에 끝나고 최종 실패를 조회·재처리할 수 있다.
- [ ] EC2 전체 중단을 외부에서 감지하고 담당자가 Discord·이메일 알림을 실제 수신한다.
- [ ] 새 DB 복원, RPO 5분·RTO 2시간, PG 대조·개인정보 재삭제를 검증했다.
- [ ] 안전한 이전 서버로 롤백할 수 있고 구버전 앱이 새 서버·오류 계약과 호환된다.
- [ ] 동의·탈퇴·보상·보관 정책이 승인됐고 앱 UI와 서버 동작이 일치한다.
- [ ] 합의한 데이터 크기·부하에서 지연·오류·정합성 목표를 만족한다.
- [ ] 전체 AWS 월 견적·사용량 제한이 8~9만 원 목표에 맞고 담당자·수신처가 지정됐다.

미통과가 남으면 보류를 유지한다. 자동 테스트 통과, 코드 리뷰 승인, 기획 정책 승인, 운영 복구 검증, 최종 출시 승인은 서로 다른 판단이다.
