# ADR-0033: 낙상 판정 입력 창과 판정 기록

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-09-20 |
| 관련 | LLD-0051, #656, ADR-0030 v2, ADR-0031, ADR-0032, 정책서 v1.1 B 1.4, 작업지시서 B10 |

## 맥락 (Context)

작업지시서 B10은 서버가 받은 IMU를 AI 판정 흐름으로 넘기는 **입구**를 만들라고 한다. 낙상 모델은 배포되지 않았고 AI가 실제로 받을 입력 형식은 다음 판에서 온다. 정책서 1.4는 판정 결과 세 값(1.4.1), 판정마다 필수 10필드(1.4.2), 인과성(1.4.4: 입력 창의 끝과 각 입력의 서버 가용 시각이 판정 시각 이하), 「알림」의 정의(1.4.5: 실제 도달)를 확정했다. 내보내기 `decisions.jsonl`(형식서 §8)과 검사기 K1~K5가 이 기록을 읽는다.

심박은 지금 샘플마다 AI를 부르고 결과를 `heart_rate_event.status`에만 남긴다(ADR-0031). 판정 기록 테이블은 없다.

결정할 것은 셋이다. 언제 판정 창을 만드는가, AI가 없을 때 무엇을 기록하는가, 판정 기록을 어디에 두는가.

## 결정 (Decision)

1. **판정 창은 충격 표시가 붙은 IMU 배치가 저장될 때 만든다.** 창 = `[trigger.ts_ms − before_sec, 그 배치의 measured_at_end_ms]`(기본 before 2초). 뒤따르는 10초를 기다리지 않는다. 늦게 오는 자료를 기다리면 판정이 늦어지고, 정책 1.4.4가 요구하는 것은 「그 시점에 가용했던 입력만 썼는가」이지 「모든 자료가 온 뒤 판정했는가」가 아니다. 창 안의 입력은 그 시점까지 **저장된** 배치만이다(`persisted_at_ms ≤ input_cutoff_ms`).
2. **AI 입구는 설정으로 켜고 끈다. 기본은 꺼짐.** 꺼져 있으면 창도 만들지 않고 기록도 없다. 모델이 배포되면 켠다. 켜져 있을 때 창에 가속도 자료가 없으면 AI를 부르지 않고 `ABSTAIN_INSUFFICIENT_INPUT`을 기록한다. AI 호출이 실패하면 **기록하지 않는다** — 「판정할 자료가 없었다」와 「판정기가 죽어 있었다」는 다른 사실이고, 후자를 세 값 중 하나로 뭉개면 1.4.1의 정신을 어긴다. 실패는 예외 종류만 로그·메트릭으로 남긴다.
3. **판정 기록은 `decision_record` 테이블 하나다.** 1.4.2 필수 10필드 + 1.4.3 선택 필드 + `alert_delivered`(형식서 §8 제안, 기본 `false`). `stream_ids_used`는 창에 들어간 배치 `batch_id` 배열을 JSON 텍스트로 둔다. 인시던트(운영 상태기계·정답 라벨)와 섞지 않는다(1.8.1).
4. **`ALERT`가 나와도 아직 알림을 보내지 않는다.** 알림 경로는 모델 배포 뒤 별도 ADR이다. 그래서 `alert_delivered`는 항상 `false`이고, 그 사실이 기록에 남는다(1.4.5).
5. **판정은 배치 저장을 막지 않는다.** 저장 뒤 트랜잭션 밖에서 돌고, 어떤 예외도 `STORED` 응답에 영향을 주지 않는다.

## 고려한 대안 (Considered Options)

1. **충격 뒤 10초를 기다렸다가 판정** — 정확도는 오르지만 판정이 10초 이상 늦고, 「기다린다」는 상태 관리(타이머·재시도)가 필요하다. 모델이 없는 지금 만들 이유가 없다. 모델이 요구하면 그때 창 규칙만 바꾼다(설정값).
2. **AI 실패를 `ABSTAIN_INSUFFICIENT_INPUT`으로 기록** — 입력 부족과 판정기 장애가 사후에 구별되지 않는다. 기각.
3. **심박 판정도 `decision_record`에 함께 기록** — 심박은 샘플마다 1건이라 하루 8.6만 행이 더 생기고, 지금 심박 AI 응답에는 `decider_version`·창 개념이 없다. 낙상 모델과 함께 다시 본다.
4. **AI 입구를 항상 켜고 응답이 없으면 무시** — 모델 없는 서버가 호출 실패 로그를 초당 수십 건 남긴다. 기각.

## 결과 (Consequences)

### 긍정
- 정책 1.4.1~1.4.5의 기록 요건이 테이블 하나로 충족되고 내보내기 `decisions.jsonl`이 K1~K5를 통과할 수 있다.
- 모델이 배포되면 설정 하나로 켠다. 입력 형식이 바뀌면 `FallAssessmentClient`의 요청 조립만 바꾼다(원문이 S3에 그대로 있다).

### 부정 / 트레이드오프
- 창이 충격 배치까지만이라 뒤따르는 보강 자이로는 판정에 들어가지 않는다. 판정 성능보다 인과성 기록을 우선한 선택이다.
- 판정 창 조립이 S3 GET을 배치 수만큼 한다(창 3초면 3~4회). 충격은 드물어 부하는 무시할 수 있다.
- `ALERT`가 나와도 아무 데도 가지 않는다. 모델 배포 전까지는 기록만 쌓인다.

## 후속 / 미결정
- AI 실제 입력 형식(AI 담당 다음 판) → `FallAssessmentClient` 요청 조립 교체.
- `ALERT` → FCM 알림 경로와 `alert_delivered` 갱신(별도 ADR).
- `severity`·`trigger_path` 값 목록(정책서 열린 항목).
- 심박 판정의 `decision_record` 기록 여부.
