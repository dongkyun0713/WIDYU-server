# ADR-0031: 심박을 배치 v2로 받아 원본을 보존하고 저장 뒤에 판정한다

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-09-20 |
| 관련 | LLD-0047, #646, ADR-0017(단건 전송 결정 대체), ADR-0008(AI 트랜잭션 경계 개정), ADR-0030 v2 |

## 맥락 (Context)

ADR-0017은 심박을 1초 단건(`/app/heart-rate/send-single`)으로 받아 AI에 동기 전달한 뒤 저장하기로 했고, ADR-0008은 AI 호출을 저장 트랜잭션 밖에 두되 AI 실패는 500으로 올려 저장을 막았다. 데이터 정책서 v1.1과 작업지시서(2026-09-19)는 이 전제를 바꿨다.

- **B5**: 심박을 샘플 배열(`bpm`·`ts_ms`·`accuracy`, 부록 B `hr`)로 받는다. 지금은 정확도가 아예 없다.
- **1.2.1 [확정]**: 값이 이상해도 저장한다. 제외는 판정 단계에서 한다. AI 실패가 저장을 막는 지금 구조는 이 규칙을 어긴다.
- **1.1.8 [확정, 필수]**: 잰 시각부터 서버 수신까지 95%가 10초 이내. 서버는 그 분포를 잴 수 있게 잰 시각과 서버 수신 시각을 따로 저장해야 한다.
- **내보내기 `hr` 스트림**(형식서 §3.5): 배치 단위 레코드 + `_server` 봉투(수신·수락·저장 시각, 계보, `payload_sha256`). 지금 `heart_rate_event`에는 이 정보가 없다.

한편 ADR-0030 v2로 IMU 배치는 이미 「원문 바이트 S3 + `sensor_batch` 인덱스 행 + 시계 매핑 + 회차 귀속 + 계보」 파이프라인을 갖췄다.

## 결정 (Decision)

1. **심박 배치는 IMU와 같은 파이프라인을 탄다.** `stream: "hr"`인 배치를 같은 endpoint(`POST /api/v1/sensor/batches`, `/app/sensor/batches/send`)로 받아 원문 바이트를 S3에, 봉투 메타를 `sensor_batch`에 저장한다. 검증만 스트림별로 갈린다. 새 endpoint·새 인덱스 테이블을 만들지 않는다.
2. **샘플은 기존 `heart_rate_event`에도 행으로 저장한다.** `accuracy`·`batch_id` 컬럼을 더한다. 상태 조회·그래프·위급 사이클·30일 정리 등 기존 기능이 바뀌지 않는다. 배치 원문과 샘플 행이 중복 저장되지만, 원문은 연구용(바이트 왕복)이고 행은 운영용(실시간 조회)이라 역할이 다르다.
3. **저장이 판정에 앞선다.** 샘플마다 AI를 호출하되 실패하면 `status=UNKNOWN`으로 저장하고 다음 샘플로 간다. 배치 안에서 AI가 한 번 실패하면 남은 샘플은 AI를 건너뛴다(응답 지연 × 샘플 수만큼 수신 스레드가 잠기는 것을 막는다). `bpm`이 `1..299` 밖이거나 `accuracy=UNRELIABLE`인 샘플은 저장만 하고 AI를 호출하지 않는다(AI가 0·300을 거부한다).
4. **순서는 S3 PUT → 샘플 행 저장(+AI) → 인덱스 행 INSERT다.** 인덱스 행이 먼저 있으면 그 뒤 샘플 저장이 실패했을 때 재전송이 `DUPLICATE`로 막혀 샘플이 영영 비는 구멍이 생긴다. 샘플 행은 `(member_id, measured_at)` UK로 멱등이라 재전송이 안전하다.
5. **기존 단건 경로는 앱이 전환할 때까지 유지한다.** 제거는 별도 이슈다.

## 고려한 대안 (Considered Options)

1. **단건 경로에 `accuracy`·`server_received_at`만 추가** — 변경이 가장 작다. 그러나 원문 보존·계보·시계 매핑이 없어 내보내기 `hr` 스트림을 만들 수 없고, AI 실패가 저장을 막는 구조는 그대로다.
2. **심박 전용 인덱스 테이블(`heart_rate_batch`)** — 컬럼이 딱 맞지만 저장·멱등·계보·귀속 코드가 두 벌이 된다. `sensor_batch`의 IMU 전용 컬럼이 null로 남는 비용이 더 싸다.
3. **샘플 행을 두지 않고 배치 원문만 저장** — 기존 조회 API를 전부 S3 읽기로 바꿔야 하고 실시간 상태 조회가 느려진다. 기각.
4. **AI를 먼저 호출하고 실패하면 거부(현행)** — 1.2.1 위반. 기각.
5. **AI를 비동기 큐로 분리** — 위급 판정이 늦어지고 아웃박스가 필요하다. 지금은 배치당 최대 60회 순차 호출 + 실패 시 단락으로 충분하다. 지연이 관측되면 다시 본다.

## 결과 (Consequences)

### 긍정
- 정책 1.2.1·1.1.8·1.3.3과 내보내기 §3.5 봉투가 한 파이프라인으로 충족된다.
- 심박·IMU가 같은 멱등·계보·귀속·시계 규칙을 쓴다.
- AI 장애가 자료 유실이 아니라 `UNKNOWN` 상태로 남는다.

### 부정 / 트레이드오프
- 같은 자료가 S3 원문과 `heart_rate_event` 행으로 두 번 저장된다.
- `sensor_batch`의 `collection_mode`·`gyro_mode`가 NULL 허용으로 바뀐다(심박에는 없는 개념). IMU는 서비스 검증이 필수를 보장한다.
- `measured_at`은 기존과 같이 Asia/Seoul `LocalDateTime`으로 둔다. 원 시각(`ts_ms`)은 원문과 인덱스 행에 남으므로 손실은 없지만, 두 시각 표현이 공존한다.
- 배치 안 AI 단락은 그 배치의 남은 샘플을 `UNKNOWN`으로 남긴다. 판정 누락이 아니라 판정 불가의 기록이다(1.4.1의 정신).

## 후속 / 미결정
- `HeartRateBatchService.storeAndAssess`의 `serverReceivedAtMs`는 지금 쓰이지 않는다. B9 지연 집계가 쓸 자리라 시그니처만 유지한다.
- 단건 경로(`/app/heart-rate/send-single`) 제거는 앱 전환 확인 뒤 별도 이슈.
- 지연 분포 계산과 재전송 제외 집계는 B9 내보내기에서.
- 심박 스트림이 IMU와 같은 `clock_mapping`을 쓸 수 있는지(코드-10)는 FE 확인 대기. 서버는 받은 `clock`을 그대로 등록만 한다.
- `HeartRateEmergency.location`은 배치에 주소가 없어 null이 된다. 위급 알림에 주소가 필요하면 별도 조회 경로가 필요하다.
