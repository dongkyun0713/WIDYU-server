## 맥락 (Context)

데이터 정책서 v1 B장 1단은 워치 가속도(mg 정수)·자이로(mrad/s 정수)·폰 IMU·폰 위치 원본을 재표본화나 보간 없이 그대로 저장하고(1.6.2, 1.6.9), 샘플별 원 측정 시각을 epoch 밀리초 UTC로(1.1.2), 자료가 판정에 쓰일 수 있게 된 서버 가용 시각을 배치 단위로(1.1.3, 1.1.4) 남기도록 확정했다. `device_id`·`session_id`·`seq`를 저장하고 재전송은 원 순번과 원 시각을 유지한 채 중복이면 한 건으로 처리한다(1.3.2, 1.3.3). 자이로가 없는 입력을 0으로 채우지 않고 평시 생략과 결측을 구별한다(1.2.6). 원시 센서 수치는 INFO 로그에 남기지 않는다(1.6.7).

합의 대기 B는 샘플 하나마다 DB 행을 만들지 않는 저장 구조를 권고한다. 가속도 1초 배치는 참가자당 하루 86,400건이라 행 단위 저장은 참가자 10명 한 달에 2,600만 행이 된다. 현재 서버에는 IMU 수신·저장 코드가 없고, 심박은 1초 단건을 `heart_rate_event`에 1행씩 저장한다.

결정할 것은 두 가지다. 배치 페이로드를 어디에 두는가, 그리고 재전송 중복을 어떻게 판별하는가.

## 결정 (Decision)

1. **배치 1건 = S3 객체 1개 + MySQL `sensor_batch` 인덱스 행 1개.** 페이로드는 S3에, 조회·삭제·귀속에 필요한 메타(스트림 종류, 배치 종류, 식별자, 측정 시각 범위, 수신 시각, 샘플 수, 바이트 수, sha256, 수집 당시 `gyro_mode`, `on_body`)는 MySQL에 둔다. 인덱스 행이 S3 객체의 유일한 목록이므로 삭제·가명화·파기는 인덱스 행을 기준으로 수행한다.
2. **멱등 키는 앱이 붙이는 불변 `batch_id`(ULID)다.** UK는 `batch_id`이고, S3 키는 `sensor/{memberId}/{deviceId}/{stream}/{batch_id}-{payload_sha256}.json`이다. 재전송은 같은 `batch_id`와 같은 원문 해시일 때만 `DUPLICATE`(PUT 없음)다. 같은 `batch_id`에 다른 원문이 오면 계약 위반으로 거부한다. 내용이 달라지는 정상 재전송(`resend` 블록)은 새 `batch_id`에 `original_batch_id`로 계보를 남긴다(지시서 B4, 정책 1.8.2). `(device_id, session_id, seq)`는 순번 누락 검사용 인덱스로만 둔다.
3. **S3 내용은 받은 원문 바이트 그대로다.** 재직렬화·정렬·압축을 하지 않는다. `payload_sha256`·`byte_size`도 원문 기준이다. 완료 기준이 「앱이 보낸 본문과 바이트 단위로 같은 값이 복원」(지시서 B2, 완료기준 C9-1)이므로 어떤 변환도 허용되지 않는다. 모르는 필드는 거절하지 않는다(원문이 보관되므로 손실이 없고, 스트림 단위로 늘어나는 구조를 막지 않는다).
4. **시각은 epoch 밀리초 BIGINT로 저장하고, 시계 환산 다섯 값은 원본 그대로 별도 컬럼에 보존한다.** 샘플 시각은 앱이 부팅 기준 나노초(문자열)로 보내고 서버가 `anchor_epoch_ms + (elapsed_ns − anchor_elapsed_ns)/1e6`으로 환산한다(정책 1.1.7). 환산값(`measured_at_start/end_ms`)과 원값(`anchor_*`, `t0_*`)을 둘 다 남겨 기준점이 바뀌면 다시 환산할 수 있다. 시각 단계(`server_received/accepted/persisted/model_available_at_server_ms`)를 하나로 합치지 않는다(지시서 B3). 기존 `LocalDateTime` 관례와 다르지만 정책 1.1.2가 스트림 시각을 epoch로 확정했고, 가용 시각과 판정 시각의 비교(1.4.4)가 같은 단위여야 한다.
5. **가속도와 자이로는 한 배치에 오되 시간축이 독립이다.** `gyro: null`은 null 그대로 저장한다(0 배열 금지). 자이로 부재가 설계된 생략인지 결측인지는 배치의 `collection_mode`(product/research)로 가린다(정책 1.2.6·1.6.4 v1.1). v1의 「스트림 분리」 설계는 부록 A 형식에 맞춰 폐기한다.
6. **S3 PUT은 수신 스레드에서 동기로 한다.** 저장이 끝난 뒤에만 `STORED`를 응답해 클라이언트의 재전송 판단이 정확하게 유지된다. `apiCallTimeout` 5초로 S3 장애 시 스레드 고갈을 막는다.

## 고려한 대안 (Considered Options)

1. **MySQL `sensor_batch` 행에 샘플 JSON 컬럼(S3 없음)** — 인프라가 하나라 삭제·가명화가 단순하다. 그러나 행당 1KB 안팎의 페이로드가 DB와 백업에 누적되고, 연구 자료 규모가 커질수록 RDS 저장·백업 비용이 정비례한다. 사용자가 저장 비용을 이유로 기각했다.
2. **S3 객체 + MySQL 인덱스 행(채택)** — 페이로드가 DB 밖으로 나가고 S3 수명주기 정책을 쓸 수 있다. 저장 지점이 둘이라 실패 순서를 정해야 한다. S3 먼저, 인덱스 다음이며 인덱스 INSERT가 실패하면 인덱스 없는 객체가 남을 수 있다.
3. **내용 해시를 S3 키에 넣어 객체를 내용별 불변으로(채택)** — 앱 계약상 `batch_id`는 불변이지만 서버는 계약 위반 입력과 동시 요청에도 DB 행과 S3 원문이 어긋나지 않아야 한다. 해시 접미사를 사용하면 서로 다른 원문이 같은 객체를 덮어쓰지 않는다. 경합에서 INSERT에 진 객체가 고아로 남을 수 있으나, 참가자 파기는 회원 접두사를 함께 삭제한다.
4. **`If-None-Match: *` 조건부 PUT으로 첫 객체를 고정** — 덮어쓰기는 막지만 412를 받은 쪽이 INSERT를 계속해야 하는데 그 행의 해시는 S3 객체와 다르고, PUT 뒤 INSERT 전에 죽은 경우와 구분할 수 없다. 내용 해시를 키에 넣는 편이 더 단순하다.
5. **배치를 시간 단위 파일로 묶어 S3에 저장** — 인덱스 행이 시간당 1개로 줄지만, 묶기 전 배치를 Redis 등에 버퍼링해야 하고 버퍼 유실이 곧 자료 유실이다. 1단에서는 배치 1건 = 객체 1개로 시작하고, 인덱스 행 수가 문제가 되면 후속으로 검토한다.
6. **`@Async`로 S3 PUT을 분리** — 수신 스레드가 빨라지지만 `STORED` 응답이 저장 완료를 뜻하지 않게 되어 재전송 판단이 깨진다. 기각한다.

## 결과 (Consequences)

### 긍정
- 정책 1.1.2~1.1.4, 1.2.6, 1.3.2·1.3.3, 1.6.2·1.6.9가 저장 구조에 1:1로 대응한다.
- 재전송 멱등성이 키 하나로 정의되어 클라이언트가 `seq`만 유지하면 된다.
- 바이트 수·sha256이 인덱스에 있어 3단 K3(연구 원본 수용 확인) 대조에 바로 쓸 수 있다.

### 부정 / 트레이드오프
- 저장 지점이 둘이라 S3 PUT 성공 뒤 INSERT 전에 프로세스가 죽으면 인덱스 없는 객체가 남는다. 같은 원문의 재전송은 같은 내용별 불변 키를 쓰고 INSERT까지 마치므로 자료 손실은 없다.
- 같은 `batch_id`에 서로 다른 원문이 동시에 오더라도 객체 키가 해시별로 갈린다. INSERT 승자 행은 자신이 올린 객체를 가리키며, 패자는 기존 행의 해시가 다르면 `DUPLICATE`가 아니라 계약 위반으로 거부된다. 패자 객체는 접두사 삭제 전까지 고아로 남을 수 있다.
- 참가자당 초당 S3 PUT 1회가 WebSocket 인바운드 스레드를 점유한다. 심박·위치 처리가 밀리면 별도 executor 또는 아웃박스로 뺀다.
- 원문을 그대로 두므로 S3 객체는 앱이 보낸 표기(공백·필드 순서·숫자 표기)를 그대로 갖는다. 서버 쪽 정규화가 필요하면 내보내기(B9)에서 한다.

## 후속 / 미결정
- 연구 참여 모델(`study_participation`)은 폐기됐다(2026-09-19, PR #618·이슈 #617 CLOSED). `sensor_batch`는 회원에만 귀속되고 연구 참여 FK를 두지 않는다. 보존 기간을 참여 단위로 강제할 필요가 생기면 그때 다시 설계한다.
- 재전송을 이후 착용자에 붙이지 않는 규칙(1.3.4)은 회원을 토큰으로 확정하는 구조에서 K2(측정회차·기기 배정) 없이는 강제할 수 없다.
- `clock_mapping` 테이블(기기 단위 매핑 검증·유효구간)은 B3 후속 PR. 회차 귀속은 B8, 서버 결정 수집 모드는 B12.
- 내보내기(B9) 시점에 S3 객체들을 회차·기기 단위 JSONL로 재조립해야 한다. 저장 레이아웃과 내보내기 레이아웃이 다르다.
- 실제 MySQL UK 경합과 S3 최종 상태를 재현하는 통합 시나리오는 미실행이다. `paymentMySqlTest`처럼 환경변수로 켜는 수동 측정 태스크로 후속에 추가한다.
- `sensor_batch` 행의 정리 기간과 S3 수명주기 정책은 정해지지 않았다. 심박 30일 삭제와 같이 갈지 별도로 정한다. 참가자 파기는 인덱스 행 삭제 + `sensor/{memberId}/` 접두사 삭제로 고아 객체까지 지운다.
- 판정 기록(1.4)과 AI 입력 형식은 2단이다.
