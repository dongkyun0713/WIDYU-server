# ADR-0040: DB 장애 중 심박 긴급 알림의 Redis 저하 경로

| 항목 | 값 |
| --- | --- |
| 상태 | Proposed |
| 날짜 | 2026-10-16 |
| 관련 | [LLD-0086](../lld/LLD-0086-degraded-emergency-alert-path.md), [LLD-0087](../lld/LLD-0087-degraded-alert-reconciliation.md), [ADR-0028](ADR-0028-fcm-durable-delivery.md), #771, #772 |

## 맥락 (Context)

심박 긴급 알림은 업무 트랜잭션에서 FCM outbox에 저장하고 커밋 후 worker가 발송한다(ADR-0028). 이 구조는 프로세스 재시작과 FCM 실패를 견디지만 **DB 자체가 응답하지 않는 동안**에는 측정값 저장과 outbox 적재가 함께 실패해 보호자에게 아무 알림도 가지 않는다. 심박 단건은 시니어 워치가 1초마다 보내므로 장애 수 분 동안 위급 샘플이 수백 건 들어와도 전부 버려진다.

큐만 바꾸면 해결되지 않는다. 수신자 해석(시니어 → 가족 → 보호자 → 활성 토큰 → 알림 설정)이 전부 DB를 읽고, 발송 직전 재검증도 DB다. 브로커에 이벤트를 넣어도 소비자가 토큰을 못 읽어 같은 자리에서 멈춘다.

운영 배치는 앱과 Redis가 같은 EC2에 있고 DB는 RDS다. 즉 DB와 Redis는 장애 도메인이 다르다. EC2가 죽으면 앱도 죽어 어떤 저장소도 알림을 살리지 못하므로, 다뤄야 할 상황은 **앱과 Redis는 살아 있고 RDS만 안 되는 경우**다. Redis는 운영에서 `appendonly yes`, `noeviction`이다.

## 결정 (Decision)

심박 단건 경로(`HeartRateService.processHeartRate`, REST·WebSocket 공통)에 **DB 없이 도는 긴급 알림 저하 경로**를 둔다.

1. **수신자 스냅샷을 Redis에 미리 둔다.** 시니어별로 이름·프로필 이미지와 보호자 활성 토큰 목록을 주기적으로(기본 5분) 한 번의 조회로 다시 만들어 TTL 24시간으로 저장한다. 보호자가 가족에서 빠지거나 탈퇴하면 커밋 후 그 가족의 스냅샷을 즉시 다시 만든다(LLD-0087).
2. **DB 접근 예외가 나면 AI 판정만 하고 위급이면 Redis Stream에 적재한다.** `DataAccessException`과 `TransactionException`만 저하 경로로 보낸다. 업무 예외(회원 없음 등)는 그대로 전파한다. 같은 시니어는 긴급 TTL(5분) 동안 한 번만 적재한다. 측정값은 저장하지 못한 채로 두며 응답은 AI 판정값으로 만든다.
3. **소비자가 DB 없이 `FcmTransport`로 발송한다.** 소비자 그룹과 pending 목록으로 ack·재시도·lease 회수를 처리하고 만료·영구 무효 토큰·재시도 초과는 ack 후 버린다. 성공 건은 보정 목록에 남겨 DB 복구 후 `fcm_notification` 이력으로 옮긴다(LLD-0087).
4. **중복은 Redis 표식으로 양방향에서 막는다.** 저하 경로가 적재할 때 `시니어별 알림 표식`을 긴급 TTL로 남기고, outbox worker는 claim 단계에서 같은 시니어의 긴급 심박 행을 보면 취소한다. DB 커밋은 됐는데 응답이 타임아웃돼 양쪽에 요청이 생기는 경우를 이것으로 막는다. Redis 조회가 실패하면 outbox는 그대로 보낸다(fail-open).
5. **Redis 부담은 상한으로 묶는다.** 스트림은 `MAXLEN ~ 10000`, 스냅샷은 TTL, 표식은 긴급 TTL이다. 운영 `noeviction`에서 꽉 차면 쓰기가 실패하므로 적재 실패는 경고 로그와 메트릭으로만 남기고 요청을 실패시키지 않는다.

범위는 심박 단건이다. 배치 v2와 낙상은 sensor 봉투 저장이 먼저라 DB 없이 판정까지 가지 못한다. 그쪽은 별도 결정으로 미룬다.

## 고려한 대안 (Considered Options)

1. **아무것도 안 함(클라이언트 재전송)** — 워치가 같은 `measured_at`으로 재전송하면 UK로 멱등 처리된다. 그러나 장애 중 위급 알림이 늦어지는 것 자체가 문제라 재전송만으로는 부족하다.
2. **Kafka** — 소비자 확장과 재생에 유리하다. 그러나 수신자 해석이 DB에 묶여 장애 중 발송을 해결하지 못하고, 단일 EC2에 브로커 하나를 두면 복제 계수 1의 장애점이 하나 더 생긴다. 생산자와 소비자가 같은 프로세스 하나라 파티션의 이점도 없다. 스냅샷은 어차피 Redis에 둬야 해서 저장소만 둘로 늘어난다.
3. **S3** — 박스 밖에 남는다. 그러나 EC2가 죽으면 보낼 주체도 죽고 5분 TTL이 지나 의미가 없다. 객체 저장소라 claim·ack·pending을 나열·삭제로 직접 짜야 하고 폴링마다 요청 비용이 붙는다.
4. **SQS** — 박스 밖 큐로는 S3보다 맞다. visibility timeout이 lease, DLQ가 재시도 상한이다. 그러나 앱이 EC2 한 대라 박스 밖 이점을 쓸 데가 없고 SDK 모듈과 LocalStack이 늘어난다. 인스턴스가 여러 대가 되면 다시 본다.
5. **Redis Streams(선택)** — 이미 설치돼 있고 CI에도 Redis가 있다. `XADD`·`XREADGROUP`·`XPENDING`·`XCLAIM`·`XACK`가 필요한 큐 동작 그대로다. 밀리초 단위라 5분 예산에 맞는다. 단점은 Redis가 새 단일 장애점이 된다는 것인데, 이미 refresh token·위치·인증 한도가 Redis에 있어 새 의존이 아니다.
6. **이벤트에 수신자를 싣기 vs 스냅샷** — 이벤트 발생 시점에 DB가 없으므로 수신자를 그때 해석할 수 없다. 미리 만든 스냅샷만 가능하다.

## 결과 (Consequences)

### 긍정

- RDS 장애 중에도 심박 위급이 보호자에게 간다. 적재·발송이 DB와 무관하다.
- DB가 정상이면 기존 outbox 경로와 응답이 바뀌지 않는다. 저하 경로는 예외 분기에서만 산다.
- 양방향 표식으로 「커밋됐는데 타임아웃」 경우에도 한 번만 보낸다.
- 엔티티·DDL 변경이 없다.

### 부정 / 트레이드오프

- 스냅샷은 최대 갱신 주기만큼 낡을 수 있다. 가족 제외·탈퇴는 즉시 무효화하지만 알림 설정 변경과 토큰 교체는 다음 갱신까지 반영되지 않는다. 낡은 토큰은 FCM이 거부하므로 유실이 아니라 지연이다.
- 저하 경로는 발송 직전 재검증(회원 ACTIVE·관계·설정)을 하지 못한다. 스냅샷을 만들 때 걸러진 상태가 기준이다.
- 장애 중 측정값은 저장되지 않는다. 위급 이력(`heart_rate_emergency`)도 남지 않으며 보정은 알림 이력만 한다. 측정값 재생 버퍼는 범위 밖이다.
- 저하 경로가 알린 뒤 5분 동안 같은 시니어의 정상 경로 긴급 심박 알림은 취소된다. 현재 위급 사이클 정의(5분)와 같다.
- Redis가 함께 죽으면 저하 경로도 없다. 둘 다 죽는 경우는 다루지 않는다.
- 소비자 폴링이 평시에도 1초마다 빈 `XREADGROUP`을 한 번 한다.

## 후속 / 미결정

- 운영 기본값(`fcm.degraded.enabled`, 스냅샷 TTL·갱신 주기)은 LLD-0086 미결정 사항에서 사용자 승인으로 정한다.
- 배치 v2·낙상 경로의 저하 처리는 sensor 봉투 저장 순서를 바꿔야 하므로 별도 ADR로 다룬다.
- 운영 RDS 장애 재현은 하지 않는다. 검증은 로컬 DataSource 차단과 로컬 Redis로 한다(LLD-0087).
