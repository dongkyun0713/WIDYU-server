# ADR-0016: PG 호출은 DB 트랜잭션 밖에서 수행하고 저장한 PG 멱등 키로 복구한다

- 상태: Accepted
- 날짜: 2026-08-08

## 맥락

현재 결제 승인과 취소는 비관적 행 잠금, Toss Payments HTTP 호출, 결제·포인트 반영을 하나의 DB 트랜잭션에서 수행한다. PG 지연 시간 동안 JDBC 커넥션과 행 잠금이 유지되어 커넥션 풀이 고갈될 수 있다. 또한 PG 성공 뒤 프로세스가 종료되면 내부 반영이 누락될 수 있다.

## 결정

- 승인과 취소를 `선점 트랜잭션 → PG 호출 → 결과 반영 트랜잭션`으로 분리한다.
- 선점 트랜잭션은 PG 요청 본문과 서버 생성 UUID `pgIdempotencyKey`를 영속화한 뒤 즉시 커밋한다.
- Toss의 `Idempotency-Key` 헤더에 저장한 키를 전송한다. 같은 키로 POST를 재시도하면 Toss가 15일 동안 최초 응답을 반환한다.
- PG 호출 성공 후 프로세스가 종료되면 1분 주기 복구 스케줄러와 클라이언트 재요청이 같은 멱등 키로 PG 요청을 재실행하고, 별도 결과 반영 트랜잭션에서 내부 상태를 완료한다.
- 오류 응답은 HTTP 4xx/5xx가 아니라 Toss `code`로 분류한다. 오류 코드는 영속화하고 PG 조회 뒤 재시도 또는 선점 해제를 결정한다.
- 승인 선점은 `PaymentOrder.APPROVING`과 `approvalPaymentKey`, `approvalPgIdempotencyKey`, `approvalRequestedAt`으로 표현한다.
- 취소 선점은 `PaymentCancel.PENDING` 레코드와 `pgIdempotencyKey`로 표현한다. 포인트는 선점 시 차감해 예약하고 완료 시 `Payment` 취소 누적값을 반영한다. 예약 반환 결정은 [ADR-0012](ADR-0012-payment-cancel-idempotency.md)를 따른다. 현재 전체 흐름은 [Payment Architecture](../architecture/payment.md)에 정리한다.

## 대안

1. 현재처럼 PG 호출을 트랜잭션에 포함한다: 구현은 단순하지만 PG 지연이 DB 커넥션·행 잠금을 점유한다.
2. `NOT_SUPPORTED`로 PG 메서드만 감싼다: 외부 호출 동안 기존 트랜잭션의 커넥션은 반납되지 않아 풀 점유를 해결하지 못한다.
3. 웹훅만 사용한다: 빠른 반영에는 유용하지만 유실·지연을 독립적으로 보정할 수 없다.
4. 별도 outbox/메시지 브로커를 도입한다: 더 강한 운영 제어를 제공하지만 현재 한 종류의 PG 요청에는 상태 저장과 멱등 재시도보다 복잡도가 크다.

## 결과 및 후속 위험

- PG 호출 시간에는 JDBC 커넥션과 비관적 락을 보유하지 않는다.
- 결과 반영 트랜잭션은 동일 결제·취소 행을 다시 잠가 멱등하게 완료한다.
- 승인 인증 유효시간(10분)이 지나거나 취소 멱등 키 보존 기간(15일)을 넘기면 자동 POST만 중단하고 처리중 상태를 보존해 오류 로그와 운영 대사를 요구한다.
- 복구는 `next_retry_at`으로 제어한다. 첫 조회는 선점 2분 뒤, 이후에는 지수 백오프를 적용한다. 단일 API 인스턴스를 전제하며, 다중 인스턴스로 확장할 때 ShedLock 같은 스케줄 락을 추가한다.
- 비동기 결제수단의 즉시 반영 또는 더 짧은 복구 SLA가 필요해지면 Toss 웹훅을 보조 신호로 추가한다. 웹훅은 PG 조회 또는 멱등 재시도를 대체하지 않는다.
