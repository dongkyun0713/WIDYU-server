# ADR-0022: 심박 처리 병목 측정 방법

> Architecture Decision Record. 하나의 중요한 의사결정과 그 이유를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-09-08 |
| 관련 | LLD-0026, #546 |

## 맥락 (Context)

심박 단건 경로는 시니어 한 명당 초당 WebSocket 메시지와 저장 트랜잭션을 한 번 발생시킨다.
기존 배치 경로는 15초마다 15개 값을 보내고 AI를 순차 호출한다. 동시 접속자가 늘었을 때
WebSocket 처리 스레드, AI HTTP, 저장, 동기 긴급 알림 중 어느 단계가 병목인지 측정한 자료가 없다.

기존 `k6/load-test.js`는 인증이 없는 HTTP `/test`만 호출하므로 STOMP SEND부터 사용자 ACK까지의
지연, 사용자별 순서, 유실과 중복을 확인할 수 없다.

## 결정 (Decision)

k6를 유지하고 SockJS WebSocket 위에서 STOMP 프레임을 직접 교환하는 별도 시나리오를 추가한다.
요청 `measuredAt`과 ACK의 `measuredAt`을 상관키로 사용해 end-to-end 지연을 계산한다.

- 단건은 사용자당 1초마다 한 건, 배치는 사용자당 15초마다 15건을 보낸다.
- 60초 워밍업 뒤 5분 측정을 한 회차로 하고, 동시 사용자 1·10·25·50·100명을 각각 3회 실행한다.
- 정상과 긴급 입력을 분리하고, 실제 AI와 결정론적 AI stub 환경을 별도 실행한다.
- 원본 k6 summary, Actuator Prometheus 스냅숏, 컨테이너 자원 표본과 실행 환경을 회차별로 보존한다.
- 평균은 참고값으로만 사용하고 p95·p99, 오류율, 처리량과 자원 포화가 동시에 변하는 지점을 병목으로 본다.
- 토큰은 저장소에 커밋하지 않고 외부 CSV 파일로 주입한다.

운영 구조 변경은 이 측정 결과와 제품 SLO가 확보된 뒤 후속 ADR에서 선택한다.

## 고려한 대안 (Considered Options)

1. **HTTP 테스트만 유지** — 실행은 단순하지만 WebSocket ACK와 내부 처리 경로를 측정하지 못한다.
2. **새 부하 테스트 프레임워크 도입** — STOMP 기능을 쉽게 쓸 수 있지만 도구와 운영 방법이 이원화된다.
3. **k6에서 SockJS/STOMP를 직접 구현** — 프레임 처리 코드가 필요하지만 기존 도구와 결과 형식을 재사용하고 요청·ACK를 직접 상관시킬 수 있다.

## 결과 (Consequences)

### 긍정

- 실제 앱과 같은 WebSocket 경로의 ACK 지연과 데이터 무결성을 측정할 수 있다.
- 내부 단계별 Micrometer 지표와 end-to-end 지표를 같은 회차에서 비교할 수 있다.
- 실제 AI와 stub의 차이로 AI 연산·네트워크 기여도를 분리할 수 있다.

### 부정 / 트레이드오프

- 전체 매트릭스는 환경별 약 6시간이 걸리며 실제 AI와 stub을 모두 측정하면 약 12시간이 필요하다.
- 동시 사용자 수만큼 서로 다른 시니어 계정과 유효한 JWT가 필요하다.
- 긴급 경로는 외부 사용자에게 알림을 보내지 않도록 FCM URL과 자격증명을 테스트 대역에 고정해야 한다.
- 로컬 측정은 운영 SLO나 운영 동등 성능을 대신하지 않는다.

## 후속 / 미결정

- 운영 예상 동시 시니어 수와 향후 1년 목표 규모를 제품 담당자에게 확인한다.
- 정상 ACK와 위급 알림의 p95·p99 SLO를 확정한다.
- 운영 동등 환경의 결과로 동기 유지, bounded queue, 외부 브로커, AI batch 중 하나를 후속 ADR에서 선택한다.
