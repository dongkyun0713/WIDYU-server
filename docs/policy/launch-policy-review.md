# WIDYU 출시 정책 결정서

기획 회의에서는 아래 질문별로 선택안을 정하고 담당자와 날짜를 기록한다. 추천안은 승인 전 제안이다. 앞부분의 핵심 질문부터 결정하고, 상세 항목과 개발·법률 참고는 필요한 때 확인한다.

개정일: 2026-09-14 · 대상: 기획, 디자인, 고객지원, 개인정보 담당자

회의에서 담당자와 답변 기한을 실제 이름과 `YYYY-MM-DD`로 채운다. 결정일에는 실제 승인 날짜를 적는다. 한 질문의 승인은 다른 질문까지 포함하지 않는다. 상세 질문도 마지막 결정 기록표에 한 줄씩 추가한다.

- **확정:** 요청자 또는 승인자의 선택 근거가 있다. 구현 완료와는 별개다.
- **현재 동작:** 점검 당시 코드에서 확인한 내용이며 정책 승인은 아니다.
- **제안:** 추천안이 있지만 아직 승인되지 않았다.
- **미정:** 상품 방향이나 필요한 입력값을 먼저 정해야 한다.
- **법률 확인 필요:** 선택안에 적용되는 법률을 확인한 뒤 확정한다.

## 3. 핵심 질문 상세

### 3.1 누가 포인트를 사용해 앨범을 여는가?

| 항목 | 논의할 내용 |
| --- | --- |
| 상황 | 가족의 유료 앨범을 열 때 누가 돈을 내고 누가 열람하는지 정해야 한다. |
| 결정 질문 | 포인트를 사용해 앨범을 여는 사람은 누구인가? |
| 선택지 A | 시니어만 포인트를 사용해 연다. |
| 선택지 B | 보호자만 포인트를 사용해 연다. |
| 선택지 C | 시니어·보호자 모두 각자 포인트로 연다. |
| 추천·이유 | 상품 기획 확인 후 선택. 현재 코드와 기존 설명이 달라 코드만으로 결정할 수 없다. |
| 사용자 영향 | 충전할 사람, 잔액을 보여줄 화면, 열람 권리와 환불받을 사람이 달라진다. |
| 현재 동작 | 시니어가 앨범을 연다. 기존 문서에는 보호자로 설명된 부분이 있다. |
| 안내 문구 | “[확정된 이용자]가 포인트를 사용하면 이 앨범을 볼 수 있습니다.” |

### 3.2 가족 해제 후 과거 앨범도 볼 수 없게 할까?

| 항목 | 논의할 내용 |
| --- | --- |
| 상황 | 연결을 해제한 이용자가 이전에 공유받은 앨범을 다시 열려고 한다. |
| 결정 질문 | 연결 해제 후에도 과거 앨범을 볼 수 있게 할까? |
| 선택지 A | 과거 앨범을 포함해 모든 공유 정보의 접근을 차단한다. |
| 선택지 B | 새로운 공유만 중단하고 과거 앨범은 계속 볼 수 있게 한다. |
| 개발팀 추천 | A안. 연결 해제로 공유를 중단하려는 이용자의 의도를 반영할 수 있다. |
| 사용자 영향 | A안은 이전 유료 앨범도 볼 수 없어진다. B안은 해제한 가족에게 과거 사진이 계속 보일 수 있다. |
| 별도 결정 | 유료 앨범의 포인트 보상은 3.3에서 따로 승인한다. |
| A안 안내 문구 | “연결을 해제하면 이전에 공유한 앨범을 포함해 서로의 공유 정보를 볼 수 없습니다.” |

새로운 위치·심박 공유는 가족 해제와 함께 중단한다. 이미 이용자가 내려받은 사진·영상까지 회수한다고 안내하지 않는다.

### 3.3 가족 해제로 못 보게 된 유료 앨범을 보상할까?

- **선택지:** 사용 포인트 전부 반환 / 정해진 기간·조건에 해당할 때 반환 / 보상 없음.
- **추천·이유:** 반환 기준 마련을 추천한다. 해제·재연결을 반복해 보상을 받는 경우와 기존 판매 안내를 확인한 뒤 범위를 정한다.
- **사용자 영향:** 보상 여부에 따라 열람자는 접근권과 사용 포인트를 모두 잃을 수 있다. 작성자 탈퇴와 달리 스스로 가족을 해제할 수 있는 상황도 포함한다.
- **반환안 문구:** “가족 연결 해제로 앨범을 볼 수 없어 [확정 기준]에 따라 포인트를 돌려드렸습니다.”

반환 대상·포인트 종류·지급 시점은 각각 승인한다. 다음의 작성자 탈퇴 보상과는 별도 결정이다.

### 3.4 작성자 탈퇴로 삭제된 유료 앨범을 보상할까?

| 항목 | 논의할 내용 |
| --- | --- |
| 상황 | 포인트를 내고 열었던 앨범이 작성자 탈퇴로 삭제된다. |
| 결정 질문 | 열람자에게 사용한 포인트를 돌려줄까? |
| 선택지 A | 해당 앨범에 사용한 포인트를 모두 돌려준다. |
| 선택지 B | 열람 후 일정 기간 이내 등 정해진 조건에 해당하면 돌려준다. |
| 선택지 C | 보상하지 않는다. 기존 판매 안내와 법률 적용 확인이 선행돼야 한다. |
| 개발팀 추천 | A안을 우선 검토. 열람할 수 없어진 이유와 보상을 이해하기 쉽다. 비용·악용 가능성은 확인해야 한다. |
| 사용자 영향 | A안은 사용 포인트를 회복한다. B안은 같은 앨범이라도 구매 시점 등에 따라 보상이 달라진다. |
| A안 안내 문구 | “작성자의 탈퇴로 앨범이 삭제되어 사용한 포인트를 돌려드렸습니다.” |

반환할 포인트의 종류, 반환 시점, 이미 환불·보상받은 건의 제외 기준도 각각 기록한다.

### 3.5 탈퇴 시 남은 유상 포인트를 어떻게 처리할까?

**상황:** 돈으로 충전한 포인트가 남은 이용자가 탈퇴하려고 한다. 아래는 각각 별도 결정이다.

| 결정 질문 | 선택지 | 추천·이유와 사용자 영향 |
| --- | --- | --- |
| 환불은 어디서 신청할까? | 탈퇴 화면 / 고객지원 | 탈퇴 화면 추천. 탈퇴 후 문의 경로를 다시 찾는 불편을 줄임 |
| 환불과 탈퇴의 순서는? | 환불 신청 후 탈퇴·정산 안내 / 정산 후 탈퇴 완료 | 전자 추천. 정산이 길어져도 계정 접근과 가족 공유를 먼저 종료할 수 있음 |
| 일부 사용한 상품의 환불 금액은? | 미사용 유상분 기준 / 상품별 기준 | 미사용 유상분을 구분하는 안 추천. 보너스·수수료·철회 권리를 확인한 뒤 승인 |

문구 초안: “남은 유상 포인트의 환불을 신청할 수 있습니다. 대상 금액과 처리 방법을 확인해 주세요.” 금액·처리 기한·예외는 법률 담당 확인 후 확정한다. 현재 코드의 취소 제한만으로 환불 불가 정책을 만들지 않는다.

### 3.6 탈퇴 후 삭제 상태는 어디서 확인할까?

| 항목 | 논의할 내용 |
| --- | --- |
| 상황 | 탈퇴로 로그아웃된 이용자가 사진 삭제가 끝났는지 확인하려고 한다. |
| 결정 질문 | 로그인할 수 없는 이용자에게 삭제 상태를 어떻게 제공할까? |
| 선택지 A | 로그인 없이 본인 확인 후 처리 상태를 보는 화면을 제공한다. |
| 선택지 B | 탈퇴 전 확인한 이메일로 접수·완료를 안내한다. |
| 선택지 C | 접수번호를 제공하고 고객지원 문의로 확인한다. |
| 개발팀 추천 | A안. 이메일이 없는 이용자도 직접 확인할 수 있다. 조회용 본인 확인 수단은 함께 정한다. |
| 사용자 영향 | A안은 직접 조회 가능, B안은 이메일 확인 필요, C안은 운영 시간에 따라 답변 대기 |
| 접수 문구 | “탈퇴 요청이 접수되었습니다. 삭제 진행 상황은 [확정된 확인 방법]에서 확인할 수 있습니다.” |
| 완료 문구 | “삭제 대상 자료의 삭제가 완료되었습니다.” 별도 보관 자료가 있으면 항목·기간을 구분해 안내 |

조회 화면은 삭제한 사진을 다시 보여주지 않는다. 조회나 안내에 필요한 연락처의 보관 기간을 따로 정한다. 처리 중에는 완료라고 안내하지 않고, 지연되면 선택한 채널로 진행 상황을 알리는 안을 추천한다.

### 3.7 건강·위치 동의를 거절하면 어떤 기능을 제한할까?

| 결정 질문 | 선택지 | 추천·이유와 사용자 영향 |
| --- | --- | --- |
| 건강정보 미동의 시 범위는? | 건강정보가 필요한 기능만 제한 / 전체 가입 흐름 재설계 | 해당 기능만 제한 추천. 다른 기능 이용까지 막지 않음 |
| 위치정보 미동의 시 범위는? | 위치·방문 인증 등 관련 기능만 제한 / 전체 가입 흐름 재설계 | 해당 기능만 제한 추천. 위치가 없어 못 쓰는 기능을 목록으로 안내 |
| 기존 이용자는 언제 동의할까? | 관련 기능 첫 진입 / 다음 로그인 | 관련 기능 진입 시 추천. 실제 동의 전 수집·공유는 중단 |
| 철회 후 기존 건강 목표 결과는? | 관련 정보 삭제 / 별도 근거가 있는 최소 결과만 유지 | 삭제안 우선 검토. 유지하려면 목적·항목·기간을 설명 |

문구 초안: “건강 기능을 이용하려면 건강정보 처리 동의가 필요합니다.” / “위치 공유가 꺼져 있습니다.” / “철회하면 이 정보의 수집과 가족 공유가 중단됩니다.”

건강정보 처리, 위치 수집, 가족에게 보여주는 범위를 구분해 동의 내용과 철회 방법을 제공한다. 기존 회원이라는 이유로 동의한 것으로 처리하지 않는다. 가족 연결만으로 본인을 대신해 동의할 권한이 생기지는 않는다.

### 3.8 긴급 알림 발송 실패 시 언제까지 다시 시도할까?

| 항목 | 논의할 내용 |
| --- | --- |
| 상황 | 긴급 사건을 감지해 알림을 보냈지만 네트워크 문제로 발송하지 못했다. |
| 결정 질문 | 실패한 긴급 알림을 언제까지 다시 시도할까? |
| 선택지 A | 즉시 발송을 시도하고, 실패한 경우 사건 발생 후 5분까지만 다시 시도한다. |
| 선택지 B | 즉시 발송을 시도하고, 실패한 경우 기획이 정한 다른 시간까지 다시 시도한다. |
| 개발팀 추천 | A안을 초기안으로 검토. 오래된 사건을 현재 긴급 상황으로 오인할 가능성을 줄인다. |
| 사용자 영향 | 5분 기다렸다가 처음 보내는 뜻이 아니다. 재시도 중에는 늦게 도착할 수 있고 시간이 지나면 발송하지 못할 수도 있다. |
| 안내 문구 | “알림이 지연되거나 도착하지 않을 수 있습니다. 기록의 발생 시각을 확인해 주세요.” |

가족 해제·정지·동의 철회 후에는 대기 중인 공유 알림도 발송하지 않는다. 알림이 응급 대응이나 의료적 판단을 보장한다고 표현하지 않는다.

### 3.9 이용자에게 장애를 어디서 공지할까?

**상황:** 로그인이나 결제가 되지 않아 이용자가 장애 여부를 확인하려고 한다. **Discord·이메일은 내부 담당자용 알림 계획**이다. 이용자 공지는 별도로 결정한다.

| 결정 질문 | 선택지 | 추천·이유와 사용자 영향 |
| --- | --- | --- |
| 이용자는 어디서 공지를 볼까? | 앱 공지 / 앱과 공개 웹 공지 / 개별 연락 | 앱과 공개 웹 공지 추천. 로그인 장애 때도 확인 가능 |

문구 초안: “현재 일부 기능 이용이 원활하지 않습니다. 확인 중이며 다음 안내는 [시각]에 드리겠습니다.” 복구 후 영향받은 기능·시간과 추가 조치를 안내한다. 개인정보 사고 통지·신고는 일반 장애 공지와 별도로 확인한다.

문구 초안: “잠시 후 다시 요청해 주세요. [남은 시간]” / “인증 요청 한도에 도달했습니다. [재시도 시각] 이후 이용해 주세요.” / “오늘 업로드 한도에 도달했습니다.”

AWS 전체 예산은 2절의 확정 조건이며 문자·결제 수수료는 별도 운영비다. 실제 비용에 맞춰 수치를 정한다. 보관 기간 만료 삭제와 업로드 한도 초과를 구분하고, 측정값을 알리지 않고 버리는 방식은 사용하지 않는다.

법률 확인이 필요한 질문은 확인자·근거·확인일도 남긴다. 승인 내용은 화면·고객지원 안내·개발 요구사항에 함께 반영한다.

위치 키의 TTL이 요청마다 갱신되면 오래된 기록이 계속 남을 수 있다. 기록별 시간·개수 상한과 Redis 복제·백업 잔존을 확인한다. 업로드는 프록시 제한과 S3 직접 업로드의 경로가 달라 같은 크기를 수용한다고 단정하지 않는다.

탈퇴 삭제는 원본·썸네일·변환본·S3 이전 버전·캐시 접근을 포함해 검증한다. 실패 작업을 재처리하고, 동의·삭제 원장을 복원 후 재적용해 탈퇴 자료가 다시 공개되지 않게 한다. 동의 대상·목적·문서 버전·시각·철회는 서버에 기록한다.

기존 계획은 EC2 t4g.medium·RDS 유지, 동시 활성 사용자 50명, 심박 20명×초당 1건을 전제로 한다. 실제 AWS 리전·사양·견적은 미확인이다. 측정이 24시간 지속되면 30일에 51,840,000건이므로 지속 시간과 보관 기간을 비용에 반영한다.

AWS 비용에는 서버·DB·스토리지·백업·전송·공인 IP·관측·DNS·개발/시험 자원·세금을 합산한다. 무료 크레딧 이후 비용을 확인하고 문자·PG 비용은 별도 집계한다. 예산 알림은 자동 지출 상한이 아니다. 초과 시 예산·이용 규모를 재합의한다.

내부 장애 알림은 운영 Discord·이메일과 호스트 외부 검사 경로를 준비한다. DB RPO 5분·서비스 RTO 2시간은 기존 계획의 검증 전 목표다. 실제 손실 간격과 감지부터 정상화까지 전체 시간을 측정한다. RDS 7일·S3 이전 버전 7일은 보관 제안이며 개인정보 삭제 예외를 별도 처리한다.
