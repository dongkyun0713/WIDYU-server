# write

읽는 사람이 문제, 달라지는 동작, 판단 근거를 순서대로 이해할 수 있게 쓴다.
기술적 의미와 프로젝트 템플릿을 보존한다. 문서를 다듬는 요청만으로 정책·API·구현을 바꾸거나 GitHub에 게시하지 않는다.

## 작성 기준

- 첫 문단에서 구체적인 문제와 결과를 밝힌다. 작업 과정의 나열로 시작하지 않는다.
- 한 문단에는 하나의 주제를 담는다. 긴 문장은 조건·동작·이유를 구분해 나누되, 앞뒤 인과관계를 연결한다.
- 추상적인 평가 대신 관찰 가능한 동작을 쓴다. “안정성을 강화했습니다”보다 “실패한 테스트의 종료 코드를 반환합니다”가 낫다.
- 주어와 동사를 분명히 한다. 기술 용어는 독자의 판단에 필요할 때 쓰고, 처음 나올 때 필요한 만큼 설명한다.
- 순서는 번호, 병렬 항목은 bullet, 같은 기준의 비교는 표로 표현한다. 짧은 설명에 제목·표·중첩 목록을 억지로 붙이지 않는다.
- 제목은 내용을 드러내고, 강조는 핵심 판단이나 주의할 동작에만 쓴다. 이모지와 상투적인 칭찬으로 문장을 채우지 않는다.
- 직접 말할 수 있는 내용을 비유·수식(mannered prose)으로 바꾸지 않는다. 꾸민 표현은 읽는 사람이 뜻을 한 번 더 해석하게 만들고, 원래 없던 뉘앙스를 더해 정확성을 떨어뜨린다. 답변·대화 문장에도 동일하게 적용한다. (근거: Claude 공식 문서 prompt engineering·writing density)
- 확정한 사실, 설계 제안, 추정을 구분한다. 미확인 내용은 문장을 매끈하게 만들기 위해 확정형으로 바꾸지 않는다.

## 문서별 적용

| 문서 | 독자가 알아야 할 내용 | 보존할 기준 |
| --- | --- | --- |
| 이슈 | 어떤 상황이 문제인지, 무엇이 되면 완료인지 | issue 스킬의 템플릿·담당자·라벨 |
| PR | 이전/이후 동작, 변경 이유, 실제 검증 결과 | pr 스킬의 템플릿, LLD 범위, 한글 존댓말 |
| ADR | 결정, 대안, 트레이드오프, 후속 리스크 | 기존 상태·결정 근거·연결 문서 |
| LLD | 입력·처리·출력·실패 동작·검증 가능한 인수조건 | API/데이터 계약, 인수조건 번호, 미결정 사항 |
| 운영 가이드 | 언제 어떤 명령을 쓰며 결과를 어떻게 판단하는지 | 실행 경로, 전제조건, 실패 시 조치 |

이슈·PR은 한글 존댓말을 쓴다. 설계·운영 문서는 기존 문체를 유지한다.
원본 스킬과 문서 템플릿을 필요한 범위만 읽고, 필수 항목을 가독성 때문에 삭제하지 않는다.

## 예시

**수정 전**

> 하네스 안정성 강화를 위해 브랜치 검증을 고도화하고 다양한 케이스를 반영했습니다.

**수정 후**

> 작업 브랜치에서 다른 worktree의 파일을 수정해도 기존 브랜치 확인을 통과했습니다. patch 대상의 실제 경로를 확인해 현재 worktree 밖의 수정을 차단합니다. 다른 worktree와 심볼릭 링크를 대상으로 한 회귀 테스트로 차단 동작을 확인했습니다.

마지막 문장은 실제로 해당 테스트를 실행했을 때만 쓴다. 미실행이면 “회귀 테스트 실행이 필요합니다”로 적는다.

## 마무리

초안을 원본·설계·diff·검증 출력과 대조한다. 수치, 파일 경로, 실행 명령, 링크, 실패·미실행 여부를 확인한다.
중복 설명과 근거 없는 형용사는 덜어내고, 읽는 사람의 결정에 필요한 제약과 미결정 사항은 남긴다.
결과는 바로 사용할 수 있는 문안으로 제공한다. 변경 이유는 사용자가 요청했거나 의미가 달라질 우려가 있을 때만 덧붙인다.
