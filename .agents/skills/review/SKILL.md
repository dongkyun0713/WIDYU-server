# review

코드의 작성자가 아니라 변경 동작과 근거를 기준으로 검수한다. 리뷰만 요청받으면 파일을 수정하지 않는다. 구현 작업의 자체 검수라면 발견한 결함을 구현 단계에서 수정한다.

## 절차

1. `git status --short --branch`로 검수 범위를 정한다.
   - 미커밋: `git diff HEAD`와 `git ls-files --others --exclude-standard`의 신규 파일 내용을 함께 확인한다. staged도 포함한다.
   - 브랜치/PR: 요청한 base와 HEAD의 merge-base를 구해 `git diff <merge-base> HEAD`를 확인한다. 작업 트리 변경은 별도로 구분한다.
   - 특정 커밋: `git show <commit>`을 확인한다. 임의로 마지막 커밋만 검수하지 않는다.
2. 루트 및 해당 영역 AGENTS.md, 관련 LLD/ADR을 읽는다. LLD가 없으면 docs/lld/README.md의 예외 기준을 적용하고 N/A 이유를 명시한다. 필요한 설계가 누락되면 결함으로 보고한다.
3. 인수조건마다 구현·테스트·실행 결과를 대응한다. `verify.sh`의 기존 결과를 확인하거나 해당 범위로 실행한다. 커밋된 변경은 반드시 `--base <merge-base>`를 전달한다.
4. 아래 항목 중 실제 변경과 관련된 것만 검수한다. 결과와 재현 가능한 문제를 보고한다.

## 검수 기준

- 공통 규칙: DTO 팩토리, Controller/Repository 경계, 모듈 배치, 삼항 금지, @Async/@Transactional. 정적 검사기가 놓치는 배치·애노테이션 순서도 확인한다.
- 인증·가족 접근: 호출자 권한, 대상 시니어와 가족 관계, 토큰 종류·만료, REST/WebSocket 경로의 인가 동등성.
- 결제·포인트·상태 전이: 중복 요청/동시성, 외부 PG와 DB 트랜잭션 경계, 실패 보상, 잔액 불변식.
- 이벤트·비동기·외부 호출: 프록시 self-invocation, 커밋 전후 발행, 실패 시 상태, 임시 파일 수명과 정리.
- 테스트: 인수조건에 대응하는 상태 검증. Mockito 단위 테스트에는 MockitoExtension + BDDMockito를 적용하고 통합 테스트에 무조건 요구하지 않는다. 외부 호출·이벤트·삭제의 verify는 허용한다.
- 엔티티/API 변경: ERD, ENUM 마이그레이션, controller/docs의 Swagger 동기화.
- admin/스크립트/설정 변경: 해당 영역의 실행 결과·입출력·오류 전파·호환성. Java 규칙을 다른 언어에 적용하지 않는다.

## 보고

결함을 먼저 `[우선순위] 파일:라인 — 재현 조건, 영향, 수정 방향`으로 보고한다. 이어서 인수조건 충족 여부, 검증 결과, 미실행/미해결 내용을 적는다. 결함이 없으면 발견된 결함이 없다고 쓰되 확인하지 못한 범위를 함께 밝힌다. 판정은 `APPROVE` 또는 `REQUEST_CHANGES`이며, 자체 검수 판정은 사람의 PR/배포 승인을 의미하지 않는다. 취향성 개선은 선택 제안으로 분리한다.
